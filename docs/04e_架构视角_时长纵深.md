# 04e 架构视角：500 小时时长纵深设计

> 角色：程序架构师 / Tech Lead
> 日期：2026-09-17
> 上游：`03_目录结构.md`、`04b_模块拆分.md`（本文引用其 §8 meta/run 分层、§8.5 成就事件总线、§7.4 debug 倍速）、`04c_数值草案.md` §7-8、`04d_测试与体验.md` §7-8
> 本文不重复数值与用例，只回答：**500 小时总时长这件事，在程序架构上要补什么、改什么、现在就要预留什么。**
>
> **基线**：主线单次通关 18h（04c §7）。500h ≈ **27 次完整周目**。本文所有设计都围绕"玩家会重开 27 次"这个数字展开。

---

## 0. 500h 对架构意味着什么（先对齐问题）

| 维度 | 单次通关（18h） | 500h（27 周目） | 架构影响 |
| --- | --- | --- | --- |
| 存档 key | 1 个 | 1 个主线 + N 个每日/挑战 | `save.ts` 必须参数化 key |
| 存档体积 | ~20KB | 主线 ~40KB + 每日挑战 ~600KB | localStorage 5MB 仍够，但要监控 |
| meta 层 | 几乎空 | prestigeHistory/codex/lifetimeStats 全填满 | meta slice 要现在就建 |
| 事件总线 | 几个 UI 事件 | 成就+图鉴+收藏三类订阅 | 规则表要按域拆分 |
| RNG | 一个种子 | 每轮新种子 + 每日种子 + 挑战种子 | RNG 实例要能多次 seed |
| 测试回归 | 跑一次主线 | 跑 3 次 Prestige + 全成就 | debug 倍速要能跨周目 |

**核心判断**：500h 不是"把数值拉长"，是"把 meta 层从空架子变成真系统"。单次通关的 run 层设计 04b 已经定完，本文只补 meta 层和横切支撑。

## 1. meta 层数据结构怎么撑 500h

### 1.1 meta 层字段全集（在 04b §8.1 的 MetaState 上扩展）

```ts
// types/game.d.ts
interface PrestigeEntry {
  round: number;                 // 第几周目（从 1 起）
  startedAt: number;             // 本周目开始时间戳
  finishedAt: number;            // 通关时间戳
  durationSeconds: number;        // 本周目时长（= finishedAt - startedAt，冗余字段便于排序）
  stardustGained: number;        // 本周目获得星尘
  endingStage: StageId;          // 通关时阶段（理论上都是 space）
  rocketsLaunched: number;
  endingBuildings: number;       // 通关时建筑总数
  endingPopulation: number;      // 通关时人口
}

interface CodexState {
  seenBuildings: string[];       // 见过的建筑 type id
  seenTechs: string[];            // 研究过的科技 id
  seenResources: string[];       // 产出过的资源 key
  seenWorkerNames: string[];     // 见过的小人名（去重，上限 500）
  seenStages: StageId[];
  unlockedSkins: string[];       // 皮肤解锁
}

interface DailyEntry {
  date: string;                  // 'YYYY-MM-DD' UTC
  seed: number;
  score: number;                 // 通关用时秒数
  cleared: boolean;
}

interface LifetimeStats {
  totalPlaytimeSeconds: number;
  totalResourcesGained: Record<ResourceKey, [number, number]>; // Decimal → [m, e]
  totalWorkersRecruited: number;
  totalBuildingsBuilt: number;
  totalRocketsLaunched: number;
  totalPrestiges: number;
  totalDeaths: number;           // v1 无战斗，恒 0
}

interface MetaState {
  // —— 04b 已有字段 ——
  prestigeCount: number;
  stardust: [number, number];   // Decimal → [m, e]
  achievements: string[];
  settings: { musicVolume: number; sfxVolume: number; offlinePopupShown: boolean };
  worldSeed: number;
  dailySeed: string;
  lastDailyResetDate: string;
  debugUsed: boolean;

  // —— 500h 新增字段（v1 schema 就留空数组/0）——
  prestigeHistory: PrestigeEntry[];       // 只留最近 50 轮，见 §1.3
  codex: CodexState;
  lifetimeStats: LifetimeStats;
  seedHistory: number[];                  // 用过的种子号（去重，上限 100）
  dailyHistory: Record<string, DailyEntry>;  // 只留最近 30 天
}
```

### 1.2 多周目 run 数据：覆盖存档，历史只存摘要

**结论：当前 run 覆盖写主线存档；历史只存 PrestigeEntry 摘要，不存完整 run 快照。**

| 方案 | 体积 | 玩家能否"回到第 3 周目继续玩" | 评价 |
| --- | --- | --- | --- |
| A. 每个周目一个完整存档 | 27 × 20KB = 540KB | 能 | 浪费，且 500h 后膨胀 |
| **B. 当前 run 覆盖 + 历史摘要** | 20KB + 5KB 摘要 | 不能（但设计上也不需要回去） | **推荐** |
| C. 当前 run 覆盖 + 云端快照（v2） | 本地 20KB | v2 云端能回看 | v2 再说 |

**为什么不需要"回到第 3 周目"**：Prestige 的设计就是"清档重开更强"，回去反而破坏循环。玩家想看历史，看 `prestigeHistory` 列表即可（第几轮、多久、拿了多少星尘）。

**关键规则**：
- Prestige 触发时：
  1. 把当前 run 的关键统计打包成 `PrestigeEntry` push 到 `meta.prestigeHistory`。
  2. 把 `meta.stardust += earned`、`meta.prestigeCount += 1`。
  3. 把 run 层重置回初始值（resources/buildings/workers/tech/stage 全部 hydrate 默认）。
  4. **不**清 `meta.codex`、`meta.lifetimeStats`、`meta.achievements`——这些跨周目累积。
- 重置 run 时，`lifetimeStats.totalResourcesGained` 要把当前 run 的累计资源**加进** lifetime，然后 run 清零。

### 1.3 prestigeHistory 裁剪策略

**规则**：只留最近 50 轮；更早的轮次合并成一行"远古历史"塞进 `lifetimeStats`。

```ts
// game/systems/prestige.ts（v2 启用）
function pushPrestigeEntry(meta: MetaState, entry: PrestigeEntry): MetaState {
  const history = [...meta.prestigeHistory, entry];
  if (history.length > 50) {
    const dropped = history.slice(0, history.length - 50);
    // 合并到 lifetime：总时长、总星尘、总火箭数
    meta.lifetimeStats.totalPrestiges += dropped.length;
    meta.lifetimeStats.totalRocketsLaunched += dropped.reduce((s, e) => s + e.rocketsLaunched, 0);
    history.length = 0;
    history.push(...dropped.slice(-1));  // 只保留第一轮作为"远古起点"
    history.push(...history.slice(1));
  }
  return { ...meta, prestigeHistory: history };
}
```

**为什么裁到 50**：
- 50 × 200B = 10KB，完全可接受。
- 玩家真在乎的是"我最近几轮多快"，不是"我第 3 轮玩了多久"。
- 500h = 27 轮，远不到 50 阈值——**v1 裁剪逻辑写好，但实际不会触发**。v2 玩家玩到 1000h+ 才需要。

### 1.4 图鉴进度 / 成就 / 皮肤存哪

全部在 `meta`，**不**在 run：
- `meta.codex`：见过一次就永久解锁，跨周目保留。
- `meta.achievements`：同上。
- `meta.codex.unlockedSkins`：皮肤是奖励，跨周目保留。

**为什么放 meta**：如果放 run，Prestige 后图鉴清空，玩家会觉得"我玩了 27 周目又回到原点"，重玩动机归零。这是 Kittens Game / Cookie Clicker 类游戏的基本原则——**meta 层是玩家的"永久财产"**。

## 2. 图鉴 / 成就 / 收藏的事件总线设计

### 2.1 统一原则：业务发事件，订阅方按规则表响应

这是 04b §8.5 已经定的原则，现在扩展到图鉴和收藏。**业务代码永远不知道图鉴/成就/收藏存在**。

### 2.2 事件分类与订阅关系

### 2.4 图鉴解锁：发事件 vs 查快照

**结论：事件型为主，快照型补漏。**

| 场景 | 方式 |
| --- | --- |
| 游戏运行中 | 业务发事件，codex store 即时更新（毫秒级） |
| 老存档迁移（v1 → v2） | 全量扫一遍当前 run state，把"已经见过但事件没发过"的条目补进 codex |
| Prestige 后图鉴跨周目保留 | codex 在 meta，run 重置不影响 |
| 老存档从没有 codex 字段 | migration 时调 `backfillCodexFromRun(run)` 一次性补 |

**为什么不做纯快照**：纯快照意味着每次打开图鉴 UI 都要扫一遍 27 个周目的历史，500h 后会卡。事件型累积，UI 直接读 `meta.codex` O(1)。

**为什么不做纯事件**：老存档迁移、debug 直接给资源跳过时，事件可能漏发。快照补漏是兜底。

## 3. 世界种子重开的存档隔离

### 3.1 三种"存档"的 key 设计

| 用途 | localStorage key | 保留时长 | 体积 |
| --- | --- | --- | --- |
| **主线当前 run** | `high_save` | 永久（直到玩家清档） | ~20-40KB |
| **每日挑战** | `high_daily_<UTCdate>` | 30 天滚动 | 每个 ~20KB，30 天 ~600KB |
| **成就/meta 层** | 已合并在 `high_save.meta` 里 | 永久 | ~20KB |
| **旧种子完整 run** | **不存** | — | 0 |

### 3.2 为什么不"一个种子一个完整存档"

| 方案 | 体积（27 周目） | 评价 |
| --- | --- | --- |
| A. 每个种子一个完整存档 | 27 × 20KB = 540KB | 浪费，玩家不会真的回去玩旧种子 |
| **B. 当前种子覆盖 + seedHistory 只存号** | 主线 20KB + seedHistory 27 × 4B = 20.1KB | **推荐** |
| C. 主存档 + 云快照（v2） | 本地 20KB | v2 后端再说 |

**关键认知**：04c §8.2 已定"种子只影响前 1 小时（原始+村庄）"。过了这个窗口，同一种子的中后期 run 没有保留价值——玩家 Prestige 重开时，本来就是想要"新体验"，不会想回到 10 小时前的那个 run。

**重开新周目的流程**：
1. 玩家点"转生"。
2. `meta.seedHistory.push(meta.worldSeed)`。
3. 新种子 = `rng.int(1, 2**31)`，写回 `meta.worldSeed`。
4. run 层重置。
5. `scene/map.ts` 用新 seed 重新生成地形。

### 3.3 每日挑战种子怎么存

**规则**：
- key = `high_daily_<UTC-YYYY-MM-DD>`，只存当天挑战的 run 快照（不存 meta）。
- 每天 UTC 0 点过期，前端启动时清理 30 天前的 key。
- 每日挑战的 seed = `hashString('high-daily-v1:' + utcDate)`（04b §8.6 已定）。
- 主线存档的 `meta.dailyHistory[date] = { seed, score, cleared }` 记成绩。

**为什么每日挑战不写主线存档**：
- 避免 debuff modifier 污染主线数值。
- 玩家"今天玩一把每日"不应该影响主线的成就/图鉴。
- 想刷每日成绩，开个独立 run，结束就删。

**清理逻辑**（启动时跑一次）：
```ts
function cleanupDailyKeys(): void {
  const cutoff = new Date(Date.now() - 30 * 86400_000);
  for (let i = 0; i < localStorage.length; i++) {
    const key = localStorage.key(i);
    if (key?.startsWith('high_daily_')) {
      const dateStr = key.replace('high_daily_', '');
      const d = new Date(dateStr);
      if (d < cutoff) localStorage.removeItem(key);
    }
  }
}
```

## 5. 性能风险

### 5.1 500h 后存档体积估算

**假设**：玩家完成 27 次周目，每次周目平均建筑 50 个、工人 50 个。

| 部分 | 单次体积 | 500h 后体积 | 说明 |
| --- | --- | --- | --- |
| 当前 run（resources/buildings/workers/tech/stage） | ~20KB | ~20KB | 永远只存当前 run |
| meta.achievements | ~1KB | ~5KB（50 个成就） | |
| meta.codex | ~2KB | ~15KB（~200 个图鉴条目） | seenWorkerNames 可能膨胀，见下 |
| meta.prestigeHistory | 0 | ~5KB（27 轮 × 200B） | 50 轮才裁剪 |
| meta.lifetimeStats | ~2KB | ~5KB | |
| meta.settings/seedHistory/dailyHistory | ~1KB | ~3KB | |
| **主线存档合计** | **~26KB** | **~53KB** | 远低于 5MB |
| 每日挑战（30 天滚动） | 0 | ~600KB | 30 × 20KB |
| **总计** | | **~650KB** | **localStorage 完全够** |

**风险点**：`meta.codex.seenWorkerNames`——名字去重，如果玩家 500h 招募了 5000 个工人，每个名字 6 字节 + JSON 开销 ~15B，5000 × 15B = 75KB。**必须硬上限**：`seenWorkerNames` 只存前 500 个去重名字，之后不再记录。

### 5.2 localStorage 5MB 上限什么时候必须迁 IndexedDB

**结论：v1 不迁，v2 在两个触发点迁。**

| 触发条件 | 动作 |
| --- | --- |
| 主线存档 > 1MB | UI 提示"存档变大，建议升级" |
| `localStorage.setItem` 抛 `QuotaExceededError` | 自动降级：先清每日挑战 key，再重试；仍失败提示用户清档 |
| v2 接后端云存档 | 同时迁 IndexedDB（云存档 + 本地 IndexedDB 双写） |

**为什么 v1 不迁**：
- 500h 才 650KB，离 5MB 还有 7 倍余量。
- IndexedDB 是异步 API，会把 save.ts 改成 async，破坏现有同步 debounce 设计。
- 业余开发时间有限，M4 之前不做。

**v1 必做的监控**（M4 落地）：
```ts
// save.ts
function saveNow(key = SAVE_KEY) {
  try {
    localStorage.setItem(key, JSON.stringify(...));
    const used = (localStore.getItem(key) || '').length;
    if (used > 1_000_000) console.warn(`[save] ${key} size=${used}B, consider IndexedDB`);
  } catch (e) {
    if (e.name === 'QuotaExceededError') handleQuotaFull();
  }
}
```

### 5.3 prestigeHistory 裁剪

已在 §1.3 定：只留最近 50 轮，更早合并到 lifetimeStats。500h = 27 轮，**v1 实际不会触发裁剪**，但代码要写好。

### 5.4 其他性能风险

| 风险 | 应对 |
| --- | --- |
| `meta.lifetimeStats.totalResourcesGained` 是 Decimal，500h 后可能到 e100 | 用 `[m, e]` 元组序列化，不存 Decimal 对象 |
| 图鉴 UI 渲染 200 个条目 | 用 React virtual list（v1 条目少，不做；v2 加） |
| 27 轮 prestigeHistory 列表 UI | 分页/虚拟滚动，v1 不做（27 条不多） |
| debug 倍速下 lifetimeStats 累积过快 | debug 模式产生的存档不写 lifetimeStats（`meta.debugUsed=true` 时跳过） |

## 6. debug 倍速怎么测 500h 内容

### 6.1 倍速与回归方案

**数学**：500h / 1000× = 0.5h = 30 分钟；500h / 10000× = 3 分钟。

**分级回归**（对齐 04d §7.2、§7.4）：

| 层级 | 倍速 | 内容 | 耗时 | 用途 |
| --- | --- | --- | --- | --- |
| **冒烟** | ×10000 | 单次主线通关（火箭发射） | ~3 分钟 | 每次改代码后跑 |
| **周目循环** | ×1000 | 3 次 Prestige（验证 meta 累积） | ~1.5h | 每次发版跑 |
| **全成就** | ×1000 + debug 给资源 | 遍历所有 ACHIEVEMENT_RULES | ~30 分钟 | M5 前跑 |
| **全图鉴** | ×1000 + debug 解锁 | 遍历所有 CODEX_RULES | ~20 分钟 | M5 前跑 |
| **每日挑战** | mock UTC 日期，×1000 | 连续 7 天种子 | ~10 分钟 | M5 前跑 |
| **真实手感** | ×1（正常速度） | M1~M3 走一遍 | ~30 分钟 | 每个里程碑跑 |

### 6.2 可行性结论

**×1000 倍速测 500h 内容，方案可行，但要满足三个前提**：

1. **倍速作用在 clock 上，不作用在 rAF 上**（04b §7.4 已定）。否则 ×1000 倍速下 accumulator 一次补 1000 个 tick，Phaser 渲染卡死。
2. **debug 模式下 `meta.debugUsed = true`**，并且：
   - 不写 `lifetimeStats`（防止测试数据污染终身统计）。
   - 不写 `prestigeHistory`（防止测试轮次进历史）。
   - 服务端 v2 拒收 debug 档。
3. **倍速上限与数字上限挂钩**：
   - ×1000 倍速跑 30 分钟现实时间 = 1800 秒 × 1000 = 1.8e6 秒 = 20 天游戏时间。
   - 按 04c 数值，20 天太空阶段产出 ~1e6 稀有矿物，远不到 break_infinity 溢出。
   - ×10000 倍速跑 3 分钟 = 180 秒 × 10000 = 1.8e6 秒，同上。
   - **安全上限：×10000，且 debug 给资源时 clamp 到 1e200**（break_infinity 安全区）。

### 6.3 不可压缩的部分

**倍速测不了的东西**（必须手动）：
- 500h 玩家的"长期情绪"——比如"我玩了 27 周目后还愿不愿意打开"。这是 UX 问题，不是测试问题。
- 跨设备存档同步（v2）。
- 真实手机性能（倍速下性能问题被掩盖）。

## 7. 对其他角色的挑战

### 7.1 对主策划（04a）

1. **500h 内容不能靠"拉长数值"**：如果只是把戴森球从 1e15 拉到 1e30，玩家会弃游。500h 必须靠"meta 层有新东西可攒"（图鉴、皮肤、成就、每日挑战）来撑。请明确 v2 皮肤/图鉴奖励是什么，否则 meta 层只是个空壳。
2. **27 周目后玩家为什么还玩？** 星尘公式 `1 + 0.10 × stardust` 在 27 周目后是 ×3.7，再往后呢？请给一个"软 cap"——比如 100 周目后星尘收益递减，避免数值无限膨胀。
3. **每日挑战的奖励不能影响主线**：否则玩家为了每日奖励逼自己上线，违背挂机游戏调性。请在 04a 里写死"每日奖励只给皮肤/星尘碎片"。

### 7.2 对数值策划（04c）

1. **lifetimeStats 要跨周目累积**：请明确"累计浆果 1e6"这种成就是按 run 内还是 lifetime 算。本文推荐 lifetime（放 meta），请确认。
2. **prestigeHistory 裁剪阈值 50 轮**：27 轮够 v1，但 v2 玩家可能玩 100 轮。请确认 50 是硬上限还是软 cap。
3. **debug 倍速下数值曲线**：×1000 倍速跑 30 分钟 = 20 天游戏时间。请确保这 20 天里不会出现"资源溢出存储上限"或"科技点瞬间买光"的边界。

### 7.3 对 QA（04d）

1. **500h 回归方案要写进测试计划**：本文 §6.1 的六级回归表，请落到 `测试组/测试计划.md`，作为 M5 验收标准。
2. **seenWorkerNames 500 上限要测**：第 501 个工人被招募时，图鉴不应该爆——这是边界用例。
3. **prestigeHistory 裁剪要测**：mock 51 个 PrestigeEntry，断言最早那轮被合并到 lifetime。
4. **debug 倍速不污染 meta**：debug 模式跑 3 次 Prestige，退出后 `meta.prestigeHistory` 应为空、`meta.lifetimeStats.totalPrestiges` 应为 0。
