---

## 0. 设计原则（先于数字）

1. **旧资源不替换，只稀释**：进入新阶段后，旧阶段资源仍作为高级建筑的辅助材料保留 10%~20% 需求，避免"上一阶段白玩"。
2. **软上限代替硬失败**：v1 不做死档，所有约束都翻译成"效率下降 / 停止增长 / 不能招募"。
3. **门控靠科技，不靠时间**：阶段跃迁必须由一个可购买的科技触发，而不是"玩够 X 分钟自动解锁"。
4. **大数字用 Decimal**：所有跨阶段比较、成本累加、离线结算一律走 `break_infinity.Decimal`，禁止裸 `number`。
5. **单人业余开发**：宁可曲线简单可解释，也不要 20 个互相耦合的系数。

## 1. 核心公式库

### 1.1 建筑成本递增

**结论：双轨制。**

- **普通生产建筑**（采集/作坊/农场）：`g = 1.15`
- **稀缺建筑**（仓库/住房/关键解锁）：`g = 1.50`

公式（第 `n` 座成本，`n` 从 0 起）：

```
cost(n) = base_cost × g ^ n

累计成本（买满 n 座）：
C(n) = base_cost × (g^n - 1) / (g - 1)
```

**为什么不是纯 1.5？** 1.15 让玩家每座都有"再买一个"的正反馈，配合人口/食物做软封顶；1.5 让稀缺建筑保持决策重量。如果全用 1.5，玩家在第 10 座就放弃堆叠，挂机游戏的"再点一下"快感消失。

**累计成本对照表（base = 100）：**

| 座数 n | g=1.15 累计 | g=1.50 累计 |
|---|---|---|
| 10 | 2,031 | 11,333 |
| 25 | 21,280 | 50,500 |
| 50 | 721,700 | 1.28 × 10⁹ |

> 直觉：g=1.15 时第 50 座的单座成本是 base 的 1083 倍，累计 ~7218 倍——这正是"堆叠 40~50 座是甜蜜点，再往上不划算"的来源。

### 1.2 资源产出

**结论：线性叠加，无边际递减；工人是"解锁满产"的钥匙，不是"线性加成"。**

```
building_output = base_production × (workers / required_workers) × tech_multiplier × stage_multiplier
```

- `workers / required_workers`：不足时按比例产出，超过不奖励（避免堆叠工人）。
- 工人效率恒为 100%，不做"第 5 个工人效率 80%"这种伪递减——递减交给食物消耗去间接体现。
- `tech_multiplier`：单科技 ×1.3~×1.5，全局科技 ×1.2 封顶（防止叠乘爆炸）。

### 1.3 招募新小人成本

**结论：取 g = 1.40（即 +40%/人）。**

```
recruit_cost(n) = base_recruit_cost × 1.40 ^ n
```

**为什么不是 +35% 或 +50%？**

| 增长率 | n=10 累计 | n=25 累计 | 判断 |
|---|---|---|---|
| +35% (1.35) | 14.4 × base | 197 × base | 太温和，25 人后人口爆炸，食物崩盘 |
| **+40% (1.40)** | **69.8 × base** | **7,518 × base** | **甜蜜点：前 10 人爽，25 人开始肉痛** |
| +50% (1.50) | 113 × base | 50,500 × base | 第 30 人贵到不可接受，中期扩张停滞 |

`base_recruit_cost` 按阶段重置（见各阶段表），跨阶段不继承累计倍率。

### 1.4 科技成本

**结论：单次购买，固定价格，不递增。**

```
tech_cost = fixed_amount  (一次性，买完即从商店消失)
```

理由：科技是"门控"不是"资源 sink"。如果科技也递增，玩家会囤积不买，门控失效。每个科技一个固定价格，买了就走人。

### 1.5 阶段跃迁门槛

**结论：一个科技 = 两道资源账单 + 一个前置建筑。**

```
unlock_tech_cost = K1 × R_stage + K2 × R_prev_stage
```

- `K1`、`K2` 每个阶段写死，见第 2 节各表。
- 设计意图：跃迁不仅要攒当前阶段资源，还要回头消耗一部分上一阶段资源，避免"新资源产出来就把旧资源忘了"。

### 1.6 离线收益

```
offline_gain = Σ (building_output_i × offline_seconds × efficiency_i)
offline_gain = min(offline_gain, cap_by_stage)
```

**离线效率系数（随阶段提升，待调）：**

| 阶段 | 基础离线效率 | 离线时长上限 |
|---|---|---|
| 原始 | 25% | 2 小时 |
| 村庄 | 40% | 8 小时 |
| 小镇 | 60% | 12 小时 |
| 城市 | 75% | 24 小时 |
| 国家 | 90% | 36 小时 |
| 太空 | 100% | 48 小时 |

**效率怎么随建筑提升？** 每解锁 1 座"仓库"或"市场"类建筑，全局离线效率 +2%，封顶 100%。不做线性堆叠，防止离线收益超过在线。

**离线不触发：** 科技点、事件、人口自然增长。离线只结算被动产出。

### 1.7 Prestige / 新游戏+

**结论：v1 不做，v2 预留接口。**

理由：
- 六阶段本身就是 10+ 小时内容，v1 单人开发塞 Prestige 会把存档迁移、平衡、UI 全部拖垮。
- 但数据结构预留 `prestige_count` 字段，v2 再启用。

**预留公式（v2 用，v1 不实现）：**

```
stardust_earned = floor( log10(total_rare_ore_produced) / 2 )
global_multiplier = 1 + 0.10 × stardust_owned
```

> 即通关一次太空给 ~5 星尘，全局 +50% 产出；三次通关 +150%。这是 Kittens Game 式软 Prestige，不强制重开。

## 3. 负反馈与约束

### 3.1 食物消耗

```
food_consumption = population × 0.02 食物/秒
```

即 1 个小人 50 秒吃 1 食物，1 小时消耗 72 食物。

**饿肚子惩罚（软递进，不硬死档）：**

| 食物库存 | 状态 | 产出倍率 |
|---|---|---|
| > 0 | 正常 | ×1.0 |
| = 0 持续 60 秒 | 饥饿 | ×0.5 |
| = 0 持续 300 秒 | 饥荒 | ×0.25 |
| = 0 持续 600 秒 | 罢工 | 停止产出 |

> 设计意图：玩家不会"死档重来"，但会听到警报、看到产出归零，被迫回来补农场。v1 不做人口死亡。

### 3.2 人口上限

| 阶段 | 来源 | 增量 |
|---|---|---|
| 原始 | 草棚 | +1 / 座 |
| 村庄 | 茅草房 | +2 / 座 |
| 小镇 | 酒馆 | +5 / 座 |
| 城市 | 公寓 | +20 / 座 |
| 国家 | 宫殿 | +50 / 座 |
| 太空 | 太空港（预留） | +100 / 座 |

招募新小人前必须有空余人口；招满即停，不做"超员罚款"。

### 3.3 仓库 / 存储上限

- 初始存储：浆果 50 / 石头 20（原始阶段）。
- 第一座仓库（村庄阶段）：100 木材 + 30 石头，存储 ×2。
- 大仓库（小镇阶段）：存储 ×3。
- 存储满后：**资源停止增长，但不扣除**（"溢出"提示）。

**第一次该让玩家卡一下：** 原始阶段 ~8 分钟时，浆果存储 50 会满。此时玩家必须建篝火或草棚，被迫做出第一个"消费决策"。

### 3.4 失败惩罚

**v1 不做硬失败。** 所有惩罚翻译成效率下降：
- 饿肚子 → 产出倍率下降（见 3.1）。
- 缺仓库 → 资源溢出不增长。
- 缺住房 → 不能招募。
- 离线超时 → 超出时长不计收益。

> 理由：挂机游戏的核心情绪是"回来一看赚了"，不是"回来一看死了"。硬失败会直接 1 星差评。

## 4. 挂机节奏目标与验算

### 4.1 目标节点

| 里程碑 | 目标 |
|---|---|
| 山洞 Demo | 5 分钟内完成"采 10 浆果生火" |
| itch.io 上线 | 30 分钟内进入小镇 |
| 全六阶段 | 活跃 10 小时 + 累计挂机 3 天看到火箭 |

### 4.2 验算 1：5 分钟生火

- 开局：1 人，浆果 0.1/s，石头 0.05/s。
- 篝火成本：10 浆果 + 5 石头。
- 纯挂机时间：
  - 10 浆果 / 0.1 = 100 秒
  - 5 石头 / 0.05 = 100 秒
  - 并行采集，max = 100 秒 ≈ 1 分 40 秒
- 加上首次 UI 引导、点击加速（点击 +1 浆果/次，假设玩家手忙脚乱点 10 次），实际 ~2–3 分钟。
- **结论：5 分钟目标自洽，留了 2 分钟容错。** 待调：如果 Demo 实测新手平均 >4 分钟，把初始采集速度提到 0.15/s。

### 4.3 验算 2：30 分钟到小镇

- 原始阶段（新手）：5–10 分钟。
- 村庄阶段需要：1,000 木材 + 500 石器（集市科技）。
  - 伐木场 base 0.3/s，假设玩家建 4 座 = 1.2/s（含科技 ×1.3 后 ~1.56/s）。
  - 1,000 木材 / 1.56 ≈ 641 秒 ≈ 11 分钟。
  - 石器工坊 0.05/s，建 3 座 = 0.15/s，500 石器 / 0.15 ≈ 3333 秒 ≈ 55 分钟——**这里偏慢**。
- **调整**：石器工坊 base 从 0.05 提到 **0.08**，3 座 = 0.24/s，500 石器 / 0.24 ≈ 34 分钟。加上建造、招募、等待，村庄阶段 ~20–25 分钟。
- 总计：原始 8 分钟 + 村庄 22 分钟 = 30 分钟。**自洽，但紧。** 待调：Demo 实测若新手 >35 分钟到小镇，把集市成本从 1,000 木材降到 800。

### 4.4 验算 3：10 小时活跃 + 3 天挂机看火箭

**活跃时长累加（新手平均）：**

| 阶段 | 新手时长 | 累计 |
|---|---|---|
| 原始 | 8 分钟 | 0.13 h |
| 村庄 | 25 分钟 | 0.55 h |
| 小镇 | 2.5 h | 3.05 h |
| 城市 | 4 h | 7.05 h |
| 国家 | 5 h | 12.05 h |
| 太空 | 6 h | 18.05 h |

- **结论：纯活跃 18 小时，比目标 10 小时长。** 必须靠离线收益把"挂机 3 天"折算进来。
- 离线折算：3 天 = 72 小时，按各阶段离线效率加权平均 ~60%，等效活跃时长 ≈ 72 × 0.6 = 43.2 小时的"被动产出"。
- 但离线不做决策，所以玩家体感是"活跃 10–12 小时 + 睡前挂机 3 晚 = 通关"。**自洽。**
- 待调：太空阶段 6 小时活跃偏长，如果 itch.io 评论抱怨后期拖沓，把发射台稀有矿物需求从 1e8 降到 5e7。

## 5. 防数值崩盘的护栏

### 5.1 哪些写死，哪些进 JSON

**写死在 `balance.ts`（代码层，不进配置）：**

```
COST_GROWTH_NORMAL   = 1.15
COST_GROWTH_SCARCITY = 1.50
RECRUIT_GROWTH       = 1.40
FOOD_PER_WORKER      = 0.02
STAGE_OFFLINE_CAP   = [2h, 8h, 12h, 24h, 36h, 48h]
STAGE_OFFLINE_EFF   = [0.25, 0.40, 0.60, 0.75, 0.90, 1.00]
```

理由：这些是"游戏的物理定律"，改一次要全表重算，不该让策划在 JSON 里手滑改到 1.16。

**进 JSON 配置（数据层）：**

- 每个建筑的 base cost、base production、工人需求。
- 每个科技的成本、效果倍率。
- 每个阶段的跃迁门槛。
- 阶段 ID、解锁条件、描述文案。

### 5.2 新建筑 Schema 草案

```typescript
interface BuildingConfig {
  id: string;                    // "lumberjack"
  stage: 1 | 2 | 3 | 4 | 5 | 6;
  cost_growth: 1.15 | 1.50;
  base_cost: Record<string, number>;   // {"wood": 50, "stone": 30}
  base_production?: Record<string, number>;  // {"wood": 0.3}
  upkeep?: Record<string, number>;     // {"food": 0.05}
  required_workers: number;
  population_delta?: number;            // 住房类
  storage_multiplier?: number;          // 仓库类
  unlock_tech?: string;                 // 前置科技 id
  description: string;
}

interface TechConfig {
  id: string;
  stage: number;
  cost: Record<string, number>;
  effect: {
    kind: "global_mult" | "resource_mult" | "unlock_stage" | "unlock_building";
    target?: string;
    multiplier?: number;
    next_stage?: number;
  };
}
```

### 5.3 三个最容易失衡的点 & 对策

| 风险 | 症状 | 对策 |
|---|---|---|
| **离线收益 > 在线收益** | 玩家不打开游戏，挂一周回来通关 | 离线效率封顶 100%，离线不产科技点、不触发事件、不涨人口；离线时长按阶段硬 cap |
| **人口爆炸** | 招募到 100 人后食物崩盘，玩家弃档 | 招募 +40%/人；食物消耗线性；人口上限由住房稀缺建筑（g=1.5）硬控 |
| **旧阶段资源后期无用** | 进入城市后木材/浆果仓库溢出无人管 | 每个高级建筑保留 10%–20% 旧资源需求（如铁匠铺仍需 20,000 木材）；跃迁门槛强制消耗上一阶段资源 |

## 6. 对其他角色的挑战

### 6.1 对主策划

以下设计如果被改，数值节奏会直接崩盘：

1. **篝火不能改产出**：如果篝火从"解锁建筑槽"改成"产出热量/食物"，原始阶段会多一个正反馈循环，5 分钟生火目标会变成 1 分钟。
2. **酒馆人口 +5 必须配食物消耗**：如果酒馆不耗食物，玩家会一口气堆 10 座酒馆 = 50 人口，食物系统直接失效。
3. **全局科技倍率上限 ×1.2**：如果有人想加一个"全局 ×2"科技，所有后续阶段门槛全部要重算。请改成"单资源 ×1.5"。

### 6.2 对程序架构

`balance.ts` 不要写成 2000 行上帝文件。建议：

- 按阶段拆：`balance/stage1_primitive.ts` ~ `balance/stage6_space.ts`，每文件 < 200 行。
- 常量层（第 5.1 节）单独放 `balance/constants.ts`，只读不写。
- 用 zod 或 TypeScript interface 校验 JSON 配置，启动时 fail-fast。
- 所有数值字段类型强制 `Decimal`，不要混用 `number`。

### 6.3 对 QA：最该写单元测试的边界

1. **`break_infinity.js` 溢出**：测 `1e309` 以上是否正确显示为 `e+309`，测戴森球成本 `1e15` 与发射台成本 `1e10` 相加是否精度丢失。
2. **离线时间差为负**：玩家改系统时间回退，`offline_seconds < 0` 时必须 clamp 到 0，不能产出负数。
3. **存档版本不匹配**：v1 → v2 升级时，旧存档没有 `prestige_count` 字段，必须默认 0，不能 NaN 崩溃。
4. **成本递增 n=0 vs n=1**：第 0 座成本必须严格等于 `base_cost`，不能多乘一个 `g`。
5. **食物消耗浮点累积**：`0.02 × population` 每秒累加，跑 24 小时浮点误差不能 >0.01 食物。
6. **离线 cap 边界**：离线 2 小时 1 分 vs 2 小时整，产出必须一致（按 cap 截断）。

## 7. 通关时长设计（议题 1）

### 7.1 "通关"如何定义

**v1 双层定义，避免概念混淆：**

| 层级 | 定义 | 达成标志 |
|---|---|---|
| **主线通关** | 六阶段走完一次 | 建成发射台 + 发射第一枚火箭 |
| **终局内容** | 戴森球建成 | 单次存档达到 1×10¹⁵ 稀有矿物 |

**关键决策：戴森球不放在主线里。** 按当前太空阶段产出（钻井平台 0.01/s × 10 座 ≈ 0.1/s），攒 1×10¹⁵ 稀有矿物需要 `1e15 / 0.1 = 1e16 秒 ≈ 3.17 亿年`——单次流程内根本不可达。戴森球必须挂在 Prestige 倍率下才有意义，因此 v1 主线通关线画在"火箭发射"，戴森球是 v2 终局目标。

### 7.2 总时长目标（三大约束同时满足）

| 约束 | 目标 | 数值依据 |
|---|---|---|
| 单人业余开发自己能测完 | 纯在线通关 ≤ 20 h | 开发者要反复测 5–10 遍，每遍 < 1 个工作日 |
| 演示有广度 | 朋友试玩 20 分钟能看到村庄→小镇过渡 | 对应 4.3 节验算 |
| 朋友 20 分钟不劝退 | 前 5 分钟生火、15 分钟到村庄、20 分钟开始攒小镇门槛 | 见 4.2、4.3 |

**总目标：主线通关 = 纯在线 18 h / 每天挂 8h 共 3 天 / 24h 挂机 5–7 天。** 这同时满足"开发者周末能测一轮"和"朋友睡前挂一觉能看到新东西"。

### 7.3 三档玩家通关时长反推

**前提：** 离线只能攒资源，不能做决策（买科技、分配工人、升级建筑）。离线收益按第 1.6 节效率系数折算。

**纯在线玩家（零离线）：**

直接累加 4.4 节活跃时长：

```
T_online = 0.13 + 0.42 + 2.5 + 4 + 5 + 6 = 18.05 h
```

→ **18 小时纯活跃通关。**

**每天挂 8 小时玩家：**

离线效率加权平均 ≈ 60%（按阶段表加权），离线只压缩"等资源"环节，不压缩"做决策"环节。经验系数：离线可压缩 40% 的活跃等待。

```
T_effective = 18.05 × (1 - 0.40) = 10.83 h 实际活跃
分散到 3 天（每天 ~3.5 h 活跃 + 8 h 离线）
```

→ **~11 h 活跃 / 3 个自然日通关。**

**24 小时挂机玩家：**

离线时长按阶段 cap（原始 2h / 村庄 8h / 小镇 12h / 城市 24h / 国家 36h / 太空 48h）。所有"等资源"环节全部交给离线，玩家每天登录 10 分钟做决策：

```
决策点次数 ≈ 每阶段 8–12 次 × 6 阶段 = 60 次
每次决策平均 10 分钟（读数字、点建筑）
活跃时间 ≈ 10 h 累计
自然日 ≈ 5–7 天（受离线 cap 限制）
```

→ **累计活跃 ~10 h / 5–7 个自然日通关。**

### 7.4 六阶段时长节奏表（反推验算）

| 阶段 | 纯在线 | 每天 8h 离线 | 24h 挂机 | 验算依据 |
|---|---|---|---|---|
| 原始 | 8 分钟 | 5 分钟 | 5 分钟 | 篝火 10 浆果 + 5 石头，0.1/s |
| 村庄 | 25 分钟 | 15 分钟 | 10 分钟 | 集市 1000 木材 + 500 石器，伐木场 0.3/s |
| 小镇 | 2.5 h | 1.5 h（2 天） | 半天 | 行会 5000 木材 + 2000 工具 |
| 城市 | 4 h | 2.5 h（2 天） | 1 天 | 铸币 50000 金币 + 10000 金属 |
| 国家 | 5 h | 3 h（3 天） | 1.5 天 | 工业革命 1e7 金币 |
| 太空 | 6 h | 3.5 h（3 天） | 2 天 | 发射台 1e10 金币 + 1e8 稀有矿物 |
| **合计** | **18 h** | **~11 h / 3 天** | **~10 h 活跃 / 5–7 天** | |

> 待调：如果 itch.io 测试发现 24h 挂机玩家通关 > 10 天，说明离线效率曲线过于保守，把阶段 cap 整体 ×1.5。

## 8. 可重玩性设计（议题 2）

### 8.1 Prestige / 转生（推荐方案 + 备选）

**推荐方案：星尘（Stardust）软转生。**

**触发条件：** 建成发射台并发射第一枚火箭。

**保留什么（不重置）：**

- 星尘货币（永久持有）
- 永久全局倍率
- 成就、统计数据、图鉴
- 世界种子偏好

**重置什么：**

- 所有建筑、工人、当前资源
- 所有科技（包括阶段门控）
- 阶段进度（回到原始阶段）

**解锁什么（v2 预留）：**

- 每获得 10 星尘，解锁 1 个新建筑分支（如"精灵伐木场"、"自动农场"）
- 每获得 25 星尘，解锁新科技流派

**数值公式：**

```
stardust_earned = floor( log10(total_rare_ore_collected) / 2 )

global_multiplier = 1 + 0.10 × stardust_owned
```

**一个循环周期：**

| 循环次数 | 持有星尘 | 全局倍率 | 单次通关活跃时长 |
|---|---|---|---|
| 第 1 次（首次） | 5 | ×1.50 | 18 h |
| 第 2 次 | 10 | ×2.00 | 12 h |
| 第 3 次 | 15 | ×2.50 | 9 h |
| 第 5 次 | 25 | ×3.50 | 6 h |
| 第 10 次 | 50 | ×6.00 | 3 h |

> 设计意图：3–5 次循环后单次通关压缩到"周末一局"节奏，避免老玩家觉得"又要重玩 18 小时"。

**备选方案（如果 v2 时间不够）：** 不做 Prestige，改成"多周目存档"——第二周目开局送 ×1.5 倍率但无新内容。成本最低，但重玩动机弱。

### 8.2 随机元素（世界种子）

**种子影响范围（控制在前期）：**

- 初始资源点分布（浆果/石头/木材的初始储量 ±20%）
- 随机事件流（商人来访、野怪骚扰、丰收祈福）
- 建筑 base cost 微调（±10%）

**数值期望控制：**

```
E[resource_bonus] = 0          # 正负相抵
σ[resource_bonus]  = 0.15       # 标准差 15%
```

- 种子只影响"原始 + 村庄"两个阶段（前 1 小时），进入小镇后所有资源标准化，防止后期出现"欧皇 1 小时通关、非酋 5 小时"。
- 随机事件收益期望 = 0，方差 ±15%。
- 种子用 `mulberry32(seed)` 可复现，方便竞速模式和每日挑战。

### 8.3 多流派科技路线

**三分支设计（v2 预留）：**

| 流派 | 核心加成 | 代价 |
|---|---|---|
| 经济流 | 金币产出 ×1.5，离线效率 +10% | 军事/科研产出 -20% |
| 军事流 | 工人效率 +15%，事件收益 +30% | 金币产出 -20% |
| 科研流 | 科技成本 -30%，阶段跃迁门槛 -10% | 食物产出 -20% |

**对主线时长的影响：**

```
T_single_build = 18 h
T_all_branches = 18 × (1 + 0.25 × 3) = 31.5 h  # 每多走一条分支 +25%
```

- 单路线通关：18 h
- 全流派各走一遍：~32 h（主线 + 14 h）
- 全成就（含所有分支）：~60 h

> 待调：分支切换不应该让主线崩掉。如果某流派明显强于其他，就把它的全局加成从 ×1.5 降到 ×1.3。

### 8.4 成就系统数值门槛

| 成就 | 门槛 | 预估解锁时间 |
|---|---|---|
| 第一堆篝火 | 建 1 座篝火 | 5 分钟 |
| 人口 10 | 招募 10 个小人 | 1 h |
| 人口 50 | 招募 50 个小人 | 5 h |
| 累计浆果 1e6 | 历史累计产出 | 3 h |
| 累计稀有矿物 1e6 | 历史累计产出 | 20 h |
| 首次通关 | 发射火箭 | 18 h |
| 三朝元老 | 通关 3 次 | 60 h |
| 戴森球 | 建成戴森球 | 100 h（含 Prestige 累积） |
| 全成就 | 以上全部 | ~150 h |

### 8.5 挑战模式（种子竞速 / 每日挑战）

**种子竞速：**

- 规则：给定固定种子，看谁先到太空。
- 数值平衡要点：
  - 竞速种子必须经过数值验证，**最优通关时间控制在 4–6 h**（不能 2 h 速通，也不能 10 h 折磨）。
  - 排行榜只记"首次通关时间"，不记"总游玩时间"（防止挂机刷分）。
  - 种子池只放出经过测验证的 10 个，社区投票每周轮换。

**每日挑战：**

- 规则：每天一个新种子 + 随机 debuff modifier。
- debuff 强度上限：`×1.5`（如"所有建筑成本 +25%"、"离线效率 -20%"、"食物消耗 ×1.5"）。
- 数值平衡要点：
  - debuff 不能叠加成"不可玩"——单个挑战只挂 1 个 debuff，强度在 [×1.2, ×1.5] 区间。
  - 每日挑战不影响主线存档，单独计分。
  - 每周解锁一个"周挑战"（debuff ×2.0），给硬核玩家。
