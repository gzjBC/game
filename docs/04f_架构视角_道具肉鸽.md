## 0. 设计前提（先对齐）

| 项 | 已定 | 本文假设 |
| --- | --- | --- |
| 道具效果作用方式 | production 已有 `globalMult` 参数（04b §8.2） | 道具效果聚合后塞进这个参数，不改 production 主逻辑 |

## 1. Item 接口草案

### 1.1 数据结构

```ts
// types/game.d.ts

type ItemRarity = 'common' | 'uncommon' | 'rare' | 'epic' | 'legendary';

type ItemEffectType =
  // —— 数值倍率类（持续型）——
  | 'global_mult'         // 全局产出 ×1.5
  | 'resource_mult'       // 某资源产出 ×1.5
  | 'building_mult'       // 某建筑产出 ×1.5
  | 'offline_eff'         // 离线效率 +20%
  | 'worker_speed'        // 工人移动速度 ×1.2
  | 'cost_discount'       // 建造成本 -15%
  | 'storage_boost'       // 存储上限 ×2
  // —— 即时资源类（消耗型）——
  | 'give_resource'       // 立即给 X 个某资源
  // —— 永久解锁类（meta 层）——
  | 'unlock_skin'         // 解锁皮肤
  | 'unlock_codex'        // 直接点亮图鉴
  // —— 肉鸽负面效果（v2）——
  | 'curse_global_mult'   // 诅咒：全局产出 ×0.8
  | 'curse_offline_eff';  // 诅咒：离线效率 -20%

interface ItemEffect {
  kind: ItemEffectType;
  target?: string;          // resource key / building id / skin id
  value: number;            // 倍率（1.5 = +50%）或数量
  durationSeconds?: number;  // undefined = 永久（周目内或跨周目）
}

interface ItemConfig {
  id: string;                        // "lucky_berry"
  name: string;                      // "幸运浆果"
  rarity: ItemRarity;
  icon: string;                      // "items/lucky_berry.png"
  description: string;
  effects: ItemEffect[];
  source: 'drop' | 'explore' | 'merchant' | 'prestige' | 'daily' | 'start';
  dropWeight: number;                // 掉落权重，默认 1
  stageMin: StageId;                 // 最早出现阶段
  stackable: boolean;                // 是否可堆叠
  maxStack: number;                  // 堆叠上限
}

interface ItemInstance {
  uid: string;                       // 实例 id，"inv_0001"
  itemId: string;                    // 引用 ItemConfig.id
  obtainedAt: number;                // 获得时间戳
  expiresAt?: number;                // 限时道具过期时间
  active: boolean;                   // 是否正在生效（持续型道具）
  count: number;                     // 堆叠数（消耗型）
}
```

### 1.2 为什么用 discriminated union 而非布尔字段

- `effectType` 字符串 + `target/value/duration` 是 JSON 友好的，存档直接序列化。
- 加新效果类型 = 在 `ItemEffectType` 加一行 union 成员 + 在 `applyItemEffect` 函数加一个 case，不动其他道具。
- **不要**做成 class 继承树（`class ConsumableItem extends BaseItem`），存档时原型链丢失，04d E4 已警告过。

### 1.3 静态配置 JSON 化

```
game/data/items.json        ← 所有 ItemConfig，加道具不改代码
game/data/loot_tables.json  ← 每阶段的掉落表 { stage: "village", items: [{id, weight}] }
```

## 2. 背包数据存哪

### 2.1 关键决策：消耗性道具在 run，永久解锁在 meta

| 道具类别 | 例子 | 存哪 | Prestige 后 |
| --- | --- | --- | --- |
| **持续 buff**（产出 ×1.5，持续 10 分钟） | 幸运浆果、工人士气药水 | `run.activeItems` | 清空 |
| **消耗材料**（立即给 100 木头） | 木材包、石料袋 | `run.inventory` | 清空 |
| **永久解锁**（皮肤、图鉴点亮、星尘碎片） | 像素帽子、未知图鉴 | `meta` | **保留** |
| **诅咒/debuff** | 霉运符 | `run.activeItems` | 清空（但进 lifetimeStats） |

### 2.2 run 层扩展

```ts
// types/game.d.ts 在 04b/04e 的 RunState 上加：
interface RunState {
  // ...已有字段...
  inventory: ItemInstance[];        // 背包（未激活/未使用）
  activeItems: ItemInstance[];      // 激活中（持续型道具）
}
```

### 2.3 meta 层扩展

```ts
interface MetaState {
  // ...已有字段...
  ownedItemIds: string[];            // 已见过/收集过的道具 id（图鉴）
  unlockedSkins: string[];          // 皮肤（04e 已有）
  // 星尘商店已买的永久升级
  permanentUpgrades: string[];       // "auto_harvest_unlock" 等
}
```

### 2.4 为什么消耗性道具不跨 Prestige

- 肉鸽的核心爽感是"这一局我抽到了什么 build"。如果道具跨周目保留，玩家会囤着不用，每局开局就有 ×10 倍率，新周目没有新鲜感。
- 这是《以撒》《杀戮尖塔》的标准做法：周目内收集，Prestige 清空，只留 meta 进度。
- **例外**：星尘兑换的永久升级放 meta（见 §5.4）。

## 3. 道具效果怎么作用于现有系统

### 3.1 推荐方案：聚合 multiplier，不改现有业务逻辑

**原则**：道具效果不直接改 state，而是被聚合到一个 `itemMultiplier`，在 production/offline 计算时乘进去。

```ts
// game/systems/itemEffects.ts（新增）
interface EffectContext {
  resources: Record<ResourceKey, Decimal>;
  buildings: BuildingInstance[];
  workers: WorkerState[];
  tech: TechState;
  stage: StageId;
}

// 把背包里激活的道具效果聚合成一份"当前生效的修正"
function aggregateActiveEffects(run: RunState): {
  globalMult: Decimal;
  resourceMult: Partial<Record<ResourceKey, Decimal>>;
  buildingMult: Partial<BuildingTypeId, Decimal>;
  offlineEffBonus: number;
  workerSpeedMult: number;
  costDiscount: number;
  storageMult: number;
}
```

**接入点**（全部已有，只加一个参数）：

```ts
// production.computeProduction 已经接受 globalMult（04b §8.2）
// 现在改成接受完整 effects：
function computeProduction(
  input: ProductionInput,
  dt: number,
  globalMult: Decimal,          // Prestige 星尘倍率
  effects: AggregatedEffects    // 道具聚合
): Partial<Record<ResourceKey, Decimal>>;

// offline.computeOffline 同理
function computeOffline(
  snapshot, savedAt, now,
  config: { efficiency: number; maxSeconds: number },
  effects: AggregatedEffects    // 道具离线效率加成
): OfflineResult;
```

### 3.2 为什么不发事件改 state

| 方案 | 优点 | 缺点 | 评价 |
| --- | --- | --- | --- |
| A. **聚合 multiplier**（推荐） | 不改现有系统，production 自动感知 | 激活/过期时要重算聚合 | ✅ |
| B. 发事件直接改 resources | 直观 | 道具过期时要回滚资源，容易出错 | ❌ |
| C. 改 building 实例的产出字段 | 简单 | 过期时要遍历所有建筑回滚，性能差 | ❌ |

**推荐 A**：道具效果只是"计算时乘个系数"，不持久化到建筑/资源上。激活时把 item 加进 `activeItems`，过期时移出，每次 tick 重新聚合——O(activeItems.length)，通常 < 10，性能可忽略。

### 3.3 限时道具过期

- `activeItems[i].expiresAt` 存过期时间戳。
- 主循环 tick 里每秒检查一次：`if (item.expiresAt && clock.now() > item.expiresAt) deactivate(item)`。
- 过期时发 `item:expired` 事件，UI 弹"幸运浆果效果结束"。
- 离线期间限时道具**不计时**（对齐 04c §5.3：离线不触发事件），只在在线时走。

## 4. 四种获取方式的架构成本对比

> 侵入度评分 0-10：0 = 完全不碰现有代码，10 = 要改 5+ 个现有模块。

### 4.1 随机掉落（在 production tick 里 roll）

| 维度 | 评估 |
| --- | --- |
| **新增模块** | `items` slice（背包）、`dropTable.ts`（掉落表 roll） |
| **新增文件** | 2 个：`game/state/items.ts`、`game/systems/dropTable.ts` + `data/loot_tables.json` |
| **侵入度** | **3/10** |
| **侵入点** | `production.tickProduction` 末尾调一次 `rollDrops(state, dt)`；其他不动 |
| **性能影响** | 每 100ms tick roll 一次，O(1)（rng.next() + 查表），< 0.01ms。**无感知** |
| **需要新 UI** | 小：背包按钮 + 物品栏弹窗 |
| **需要新工人 AI** | 否 |
| **需要新地图层** | 否 |
| **依赖前置** | RNG 注入（M2 已有）、items slice |
| **推荐里程碑** | **M4**（city 阶段，玩家资源够多，掉落开始有意义） |

**实现草案**：
```ts
// game/systems/dropTable.ts
function rollDrops(run: RunState, dt: number, rng: Rng): ItemInstance[] {
  // 每秒钟 N% 概率掉一件，按阶段 loot table 抽
  const chancePerSecond = 0.05;   // 5%/s
  const rolls = Math.floor(dt * chancePerSecond * 10); // 10 次/秒检查
  const drops: ItemInstance[] = [];
  for (let i = 0; i < rolls; i++) {
    if (rng.next() < 0.05) {
      const itemId = rollFromTable(lootTable[run.stage.current], rng);
      drops.push(makeItemInstance(itemId));
    }
  }
  return drops;
}
```

| 维度 | 评估 |

## 6. 世界种子与道具池

### 6.1 同 seed 同道具池的实现

**规则**：seed 决定"前 N 次道具 roll 的结果序列"。

```ts
// game/systems/dropTable.ts
function rollFromTable(table: LootTable, rng: Rng): string {
  // 按权重抽
  const totalWeight = table.reduce((s, e) => s + e.weight, 0);
  let roll = rng.next() * totalWeight;
  for (const entry of table) {
    roll -= entry.weight;
    if (roll <= 0) return entry.itemId;
  }
  return table[table.length - 1].itemId;
}
```

**关键**：`rng` 是注入的 `SeededRng`（04b §8.3），同 seed 下 `rng.next()` 序列完全一致 → 同 seed 同前 N 次掉落。

### 6.2 怎么兼容"软种子"承诺（04c §8.2）

**冲突**：如果某 seed 天生掉"幸运浆果"概率高，玩家会刷 seed 刷初始档，这就是变相作弊。

**解决方案**：

1. **道具池只影响"前 1 小时"**（对齐 04c §8.2）：进入小镇阶段后，loot table 标准化，seed 不再影响道具掉落。
2. **道具效果期望值 = 0**：稀有道具（legendary）掉率低但效果强，common 道具掉率高但效果弱，长期期望一致。
3. **种子只影响"先掉什么"，不影响"总共掉多少"**：同 seed 可能第 10 分钟掉 legendary，另一个 seed 第 50 分钟掉，但 1 小时内总价值期望一致。
4. **v1 不做"seed 竞速"**：每日挑战的 seed 是服务端下发的（v2），本地 seed 玩家可以刷，但 v1 不做排行榜。

**架构落地**：
```ts
function rollDrops(run, dt, rng, clock): ItemInstance[] {
  // 进入小镇后，道具掉落不随 seed 变
  if (isAfterSoftSeedWindow(run, clock)) {
    rng.seed(0);  // 重置为标准化种子
  }
  // ...roll...
}
```

## 7. 对 M0-M5 的影响

### 7.1 v1 schema 就要预留的字段

### 7.2 里程碑建议

| 里程碑 | 做什么 |
| --- | --- |
| M0-M3 | **不做道具**。只在 schema 留空字段。M3 末把 `items.json` / `loot_tables.json` 建空文件。 |

### 7.3 现在架构不支持的地方

**没有硬伤**。所有方向都能在现有三层架构上落地：

- 随机掉落：只动 game/ 层（production 末尾 roll）。
- 商人交易：game/ 加 slice，ui/ 加面板，不动 scene。
- 探索发现：要动 scene/ 加迷雾层，但 Phaser RenderTexture 原生支持，不需要新引擎。
- 星尘兑换：纯 meta 层。

**唯一要改的现有设计**：
- `production.computeProduction` 加第四个参数 `effects`（04b §8.2 已经预留了第三个参数 `globalMult`，现在扩展成第四个）。
- `RunState` 加 `inventory/activeItems` 两个字段。
- 这两处都是"加参数/加字段"，不改现有逻辑。

## 8. 存档大小

### 8.1 体积估算

| 部分 | 单件体积 | 数量 | 总 |
| --- | --- | --- | --- |
| `ItemInstance`（含 uid/itemId/obtainedAt/active/count） | ~80B JSON | 200 个 | ~16KB |
| `activeItems`（激活中，通常 < 10） | ~80B | 10 | ~0.8KB |
| `meta.ownedItemIds`（图鉴，string[]） | ~40B/条 | 100 个 | ~4KB |
| `meta.permanentUpgrades` | ~40B | 20 个 | ~0.8KB |
| **道具系统合计** | | | **~22KB** |

**对比**：
- 04e §5.1 估算主线存档 500h 后 ~53KB。
- 加道具系统 ~22KB → **~75KB**。
- 离 localStorage 5MB 上限还有 65 倍余量。**完全可接受**。

### 8.2 优化建议

- `ItemInstance` 不存完整 ItemConfig，只存 `itemId`（引用 `data/items.json`）。
- 过期道具立即从 `activeItems` 移除，不保留。
- 消耗型道具用 `count` 字段堆叠，不每个实例单独存。
- `meta.ownedItemIds` 用 `Set<string>` 或 `Record<string, true>` 而非数组，序列化时 `Object.keys()`，去重 O(1)。

## 9. 推荐路径（架构师立场）

### 9.1 最小可行肉鸽闭环（M4）

只做随机掉落 + 背包 + 5 个 common 道具：
- 掉落：production tick 末尾 5%/s roll。
- 背包：点按钮打开，点道具激活。
- 5 个道具：
  1. 幸运浆果：global_mult ×1.5，持续 10 分钟
  2. 工人士气：worker_speed ×1.2，持续 10 分钟
  3. 木材包：give_resource(wood, 100)
  4. 离线笔记：offline_eff +20%，持续 30 分钟
  5. 小仓库：storage_boost ×2，持续 10 分钟

**工作量**：~3 天（items slice 1 天、dropTable 0.5 天、背包 UI 1 天、5 个道具效果接入 0.5 天）。

### 9.2 不推荐 v1 做的

- **探索发现（迷雾层）**：侵入度 7/10，要改工人状态机和 map 层，M5 时间不够。
- **星尘兑换商店**：依赖 Prestige，v1 还没 Prestige。
- **诅咒/debuff 道具**：肉鸽深度内容，v1 先做正向道具。
- **道具合成/升级**：复杂度高，v1 不需要。

### 9.3 v2 再考虑

- 探索发现 + 迷雾层。
- 商人交易 + 库存刷新。
- 星尘兑换永久升级。
- 诅咒道具 + 负面效果。
- 道具图鉴 UI（独立面板）。
- 每日挑战的专属道具池。

## 10. 对其他角色的挑战

### 10.1 对主策划（04a）

1. **道具效果不能破坏数值曲线**：×1.5 的全局倍率会让 18h 通关变成 12h。请明确道具是"锦上添花"还是"必需"——如果是必需，主线门槛要重算。
2. **肉鸽 = 每局不同，但 500h 玩家会腻**：请想清楚"27 周目 × 200 个道具"是不是够撑 500h，还是要加"道具合成/组合"。
3. **负面道具（诅咒）v1 做不做**：做了更有肉鸽味，但玩家可能觉得"我打游戏还受气"。

### 10.2 对数值策划（04c）

1. **道具掉落权重**：请给每个道具的 `dropWeight` 和 `stageMin`，否则我没法写 loot table。
2. **道具效果叠加规则**：两个"幸运浆果"是 ×1.5 × 1.5 = ×2.25，还是 ×1.5 + ×1.5 = ×2.0？这影响数值平衡。
3. **限时道具过期后，已乘的资源怎么办**：推荐"只影响未来产出，不回滚已得资源"。请确认。

### 10.3 对 QA（04d）

1. **道具 roll 是 RNG**：必须走注入 RNG，测试要验证同 seed 同掉落序列（对齐 04d R1-R5）。
2. **限时道具过期**：mock clock 快进 10 分钟，断言道具自动 deactivate、UI 弹通知。
3. **背包满了**：200 个道具上限后再掉落怎么办？推荐"自动转成资源"或"丢弃最低 rarity"。请给规则。
4. **道具效果叠加**：×1.5 × ×1.5 是否 = ×2.25，要测。
