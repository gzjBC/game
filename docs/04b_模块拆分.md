## 0. 全局类型草案（types/game.d.ts）

所有模块签名都依赖这组公共类型，先固定下来，避免每个 store 各写一套。

```ts
// src/types/game.d.ts
import Decimal from 'break_infinity.js';

// ---- 资源 ----
type ResourceKey =
  | 'berries' | 'wood' | 'stone' | 'food' | 'gold'
  | 'iron' | 'coal' | 'oil' | 'science' | 'rocket_part';

// ---- 建筑 ----
type BuildingTypeId = string; // buildings.json 的 key，如 "campfire" / "hut"
interface BuildingInstance {
  uid: string;                 // 实例 id，如 "b_0001"
  type: BuildingTypeId;
  level: number;
  tileX: number;
  tileY: number;
  assignedWorkerId?: string;
}

// ---- 工人 ----
type WorkerId = string;
type WorkerVisualState =
  | 'idle' | 'walking' | 'gathering' | 'carrying' | 'building' | 'dead';
interface WorkerState {
  uid: WorkerId;
  nameEn: string;
  nameZh: string;
  visual: WorkerVisualState;
  homeTile: { x: number; y: number };
  assignedBuildingUid?: string;
  carrying?: { resource: ResourceKey; amount: Decimal };
}

// ---- 科技 ----
type TechId = string;
interface TechState {
  researched: TechId[];        // 用数组而非 Set，便于序列化
  currentTechId?: TechId;
  researchProgress: number;    // 0 ~ 1
}

// ---- 阶段 ----
type StageId = 'primitive' | 'village' | 'town' | 'city' | 'nation' | 'space';
interface StageState {
  current: StageId;
  unlocked: StageId[];
  progress: number;            // 距下一阶段的进度 0~1
}

// ---- 全局聚合态（仅供 save / production 用，不是单一根 store）----
interface GameState {
  resources: Record<ResourceKey, Decimal>;
  buildings: BuildingInstance[];
  workers: WorkerState[];
  tech: TechState;
  stage: StageState;
  meta: { savedAt: number; version: number };
}

// ---- 坐标 ----
interface Tile { x: number; y: number; }
```

> **设计决定**：zustand 拆成 5 个独立 slice（resources/buildings/workers/tech/stage），**不做单一根 store**。理由：(1) 每个 slice 独立订阅，React 重渲染粒度小；(2) production 系统只 patch 资源 slice，不会触发 workers 面板刷新；(3) 序列化时按 slice 分别导出。聚合类型 `GameState` 仅作为 save/production 的入参视图。

## 1. 模块清单与接口契约

### 1.1 resources store（`game/state/resources.ts`）

- **职责**：持有所有资源的当前数量（`Decimal`），提供增减 / 校验 action，**不**知道产出逻辑。
- **输入（TS 草案）**：
  ```ts
  interface ResourcesSlice {
    values: Record<ResourceKey, Decimal>;
    add: (key: ResourceKey, amount: Decimal | number) => void;
    spend: (key: ResourceKey, amount: Decimal | number) => boolean;
    canAfford: (cost: Partial<Record<ResourceKey, number>>) => boolean;
    get: (key: ResourceKey) => Decimal;
    hydrate: (values: Record<ResourceKey, [number, number]>) => void;
  }
  ```
- **输出**：每次 `add/spend` 触发 zustand 浅比较，订阅方重渲染；`spend` 同步返回是否成功。
- **持有状态**：`values: Record<ResourceKey, Decimal>`。
- **依赖 / 被依赖**：
  - 依赖：`systems/balance.ts`（初始值）、`types/game.d.ts`、`break_infinity.js`。
  - 被依赖：`production.ts`、`offline.ts`、`buildings.ts`（购买时 spend）、`tech.ts`（研究时 spend）、所有 React 面板。
  - **越层检查**：✅ 不 import React / Phaser。
- **关键测试点（Vitest）**：
  1. **Given** 初始 `berries=0`，**When** 调 `add('berries', 10)`，**Then** `get('berries').toString() === '10'`。
  2. **Given** `berries=5`，**When** `spend('berries', 10)`，**Then** 返回 `false` 且 `berries` 仍为 5（不允许扣成负数）。
  3. **Given** `berries=100`，**When** `add('berries', new Decimal('1e308'))`，**Then** 结果等于 `1e308`（验证 Decimal 不丢精度、不转 number 科学计数法丢精度）。
  4. **Given** `berries=10, wood=5`，**When** `canAfford({berries:10, wood:5})` 返回 true，`canAfford({berries:11})` 返回 false。

### 1.2 buildings store（`game/state/buildings.ts`）

- **职责**：持有已建造建筑实例列表，提供购买 / 升级 / 分配工人 action。
- **输入**：
  ```ts
  interface BuildingsSlice {
    list: BuildingInstance[];
    buy: (type: BuildingTypeId, tile: Tile) => boolean;
    upgrade: (uid: string) => boolean;
    assignWorker: (buildingUid: string, workerId: WorkerId) => void;
    getById: (uid: string) => BuildingInstance | undefined;
    hydrate: (list: BuildingInstance[]) => void;
  }
  ```
- **输出**：购买成功时同步 `resources.spend` 并 append 实例；失败返回 false 不动资源。
- **持有状态**：`list: BuildingInstance[]`。
- **依赖 / 被依赖**：
  - 依赖：`resources` slice（通过 zustand `useResources.getState()` 跨 slice 取）、`data/buildings.json`、`balance.ts`。
  - 被依赖：`production.ts`、`ui/BuildMenu.tsx`、`scene/GameScene.ts`（订阅 list 变化来 add/destroy 视觉）。
  - **越层检查**：✅ 纯 game 层。跨 slice 调用用 `useResources.getState().spend(...)`，**禁止**把 resources 作为参数一路传下去。
- **关键测试点**：
  1. **Given** `wood=0`，**When** `buy('hut', {x:1,y:1})`，**Then** 返回 false，`list.length` 不变，wood 不被扣。
  2. **Given** `wood=20` 且 hut 定价 20，**When** `buy('hut', {x:1,y:1})`，**Then** 返回 true，`list` 多一条 `type='hut', level=1`，wood 归零。
  3. **Given** 同 tile 已有 hut，**When** 再 `buy('hut', 同tile)`，**Then** 返回 false（占位冲突校验）。
  4. **Given** 已存在 hut，**When** `assignWorker(uid, w1)`，**Then** 该实例的 `assignedWorkerId === 'w1'`。

### 1.3 workers store（`game/state/workers.ts`）

- **职责**：持有工人逻辑状态（名字 / 当前视觉状态 / 所属建筑），**不**管寻路、**不**管动画。
- **输入**：
  ```ts
  interface WorkersSlice {
    list: WorkerState[];
    recruit: (homeTile: Tile) => boolean;   // 花费 berries 招募
    setVisual: (id: WorkerId, v: WorkerVisualState) => void;
    assignTo: (id: WorkerId, buildingUid: string) => void;
    carry: (id: WorkerId, r: ResourceKey, amt: Decimal) => void;
    clearCarry: (id: WorkerId) => void;
    hydrate: (list: WorkerState[]) => void;
  }
  ```
- **输出**：`recruit` 成功时 spend berries 并 append（名字由 name generator 产生）。
- **持有状态**：`list: WorkerState[]`。
- **依赖 / 被依赖**：
  - 依赖：`resources` slice、`systems/nameGenerator.ts`、`balance.ts`（招募成本 / 人数上限）。
  - 被依赖：`ui/WorkerPanel.tsx`、`scene/GameScene.ts`、`scene/WorkerSprite.ts`。
  - **越层检查**：✅。注意 `nameGenerator` 必须放在 `game/systems/` 而非 scene 层，因为它要在 workers store 里被同步调用。
- **关键测试点**：
  1. **Given** `berries=50` 且招募价 10，**When** `recruit({x:0,y:0})`，**Then** 返回 true，list 长度+1，新工人 `nameEn` 非空、`nameZh` 非空。
  2. **Given** 已有 10 个工人（上限 10），**When** 再 recruit，**Then** 返回 false，list 不变。
  3. **Given** 工人 `w1` idle，**When** `setVisual('w1', 'gathering')`，**Then** 该工人 visual === 'gathering'。
  4. **Given** 工人 carrying berries=5，**When** `clearCarry('w1')`，**Then** `carrying === undefined`。

### 1.4 tech store（`game/state/tech.ts`）

- **职责**：持有已研究科技与当前研究进度。
- **输入**：
  ```ts
  interface TechSlice {
    researched: TechId[];
    currentTechId?: TechId;
    researchProgress: number; // 0~1
    startResearch: (id: TechId) => boolean;
    tickResearch: (dt: number) => void;   // 由调度器驱动
    has: (id: TechId) => boolean;
    hydrate: (s: TechState) => void;
  }
  ```
- **输出**：研究完成时 append 到 `researched`，触发资源/产出系数变化（production 系统读 `has()`）。
- **持有状态**：`researched: TechId[]`、`currentTechId?: TechId`、`researchProgress: number`。
- **依赖 / 被依赖**：
  - 依赖：`resources` slice、`data/techs.json`、`balance.ts`。
  - 被依赖：`production.ts`（读科技加成）、`ui/TechTree.tsx`、`stage.ts`（阶段解锁条件里包含科技）。
  - **越层检查**：✅。
- **关键测试点**：
  1. **Given** 无科技且科学点足够，**When** `startResearch('pottery')`，**Then** `currentTechId === 'pottery'` 且扣资源成功。
  2. **Given** 正在研究 pottery（需 10 秒），**When** `tickResearch(5)` × 2，**Then** `researched` 包含 'pottery' 且 `currentTechId === undefined`。
  3. **Given** 正在研究 A，**When** `startResearch('B')`，**Then** 返回 false（一次只能研究一个）。
  4. **Given** 已研究 pottery，**When** `has('pottery')`，**Then** true。

### 1.5 stage store（`game/state/stage.ts`）

- **职责**：当前文明阶段、已解锁阶段、距下一阶段的进度。
- **输入**：
  ```ts
  interface StageSlice {
    current: StageId;
    unlocked: StageId[];
    progress: number;
    updateProgress: (dt: number) => void;
    tryAdvance: () => boolean;   // 进度满时升级阶段
    isUnlocked: (s: StageId) => boolean;
    hydrate: (s: StageState) => void;
  }
  ```
- **输出**：阶段切换时广播 `bus.emit('stage:changed', {from, to})`，scene 层监听后切换 tileset / 背景。
- **持有状态**：`current / unlocked / progress`。
- **依赖 / 被依赖**：
  - 依赖：`data/stages.json`（每阶段解锁条件）、`buildings/tech/workers` slices（读条件）。
  - 被依赖：所有 UI 面板（决定能看到哪些建筑/科技）、`scene/GameScene.ts`。
  - **越层检查**：✅。注意 stage store 不能直接 import scene，阶段切换的视觉变更通过 bus 事件解耦。
- **关键测试点**：
  1. **Given** current='primitive'，进度条满，**When** `tryAdvance()`，**Then** current='village' 且 unlocked 包含 'village'。
  2. **Given** current='village'，**When** `isUnlocked('town')`，**Then** false（town 还没解锁）。
  3. **Given** 进度 0.9，**When** `updateProgress(0.2)`，**Then** progress 钳制在 1.0 不溢出。
  4. **Given** 存档里 current='town'，**When** hydrate，**Then** `unlocked` 至少包含 primitive/village/town。

### 1.6 production system（`game/systems/production.ts`）

- **职责**：纯函数，按当前建筑/工人/科技配置与 `dt`（秒），返回本 tick 的资源增量。
- **输入**：
  ```ts
  interface ProductionInput {
    buildings: BuildingInstance[];
    workers: WorkerState[];
    tech: TechId[];
    stage: StageId;
  }
  function computeProduction(input: ProductionInput, dt: number): Partial<Record<ResourceKey, Decimal>>;

  // 调度器里调用的 action 版本（写 zustand）
  function tickProduction(dt: number): void;
  ```
- **输出**：`tickProduction` 内部调 `useResources.getState().add(...)`；`computeProduction` 是纯函数返回增量，便于测试。
- **持有状态**：无（无状态系统，所有数据从 zustand 读）。
- **依赖 / 被依赖**：
  - 依赖：所有 5 个 slice、`data/buildings.json`（产出速率）、`balance.ts`（效率系数）。
  - 被依赖：`game/loop.ts`（主循环调度器）。
  - **越层检查**：✅。
- **关键测试点**：
  1. **Given** 1 个浆果丛建筑、无工人分配，**When** `tickProduction(1)`，**Then** berries 增量为 0（必须有人工作才产出）。
  2. **Given** 浆果丛 + 1 个分配的工人，速率 1 berries/s，**When** `tickProduction(2)`，**Then** berries +2（Decimal 精确）。
  3. **Given** 已研究 'pottery'（浆果效率 ×1.5），**When** 同上，**Then** berries 增量为 3 而非 2（验证科技加成生效）。
  4. **Given** 阶段='village'，**When** 计算，**Then** primitive 专属建筑产出应为 0（跨阶段建筑不产出）。

### 1.7 offline system（`game/systems/offline.ts`）

- **职责**：根据上次保存时间戳与现在的差值，计算离线期间应得的资源。
- **输入**：
  ```ts
  interface OfflineResult {
    gain: Partial<Record<ResourceKey, Decimal>>;
    secondsElapsed: number;
    capped: boolean;         // 是否达到离线封顶
  }
  function computeOffline(
    snapshot: ProductionInput & { savedAt: number },
    now: number,
    config: { efficiency: number; maxSeconds: number }
  ): OfflineResult;
  function applyOffline(result: OfflineResult): void;  // 写 resources
  ```
- **输出**：离线收益按 `efficiency`（v1 取 0.5）打折，超过 `maxSeconds`（v1 取 8h）按封顶算。
- **持有状态**：无。
- **依赖 / 被依赖**：
  - 依赖：`production.computeProduction`（复用同一套产出公式，避免双份数值）、`balance.ts`。
  - 被依赖：`main.tsx` 启动流程、`save.ts`。
  - **越层检查**：✅。
- **关键测试点**：
  1. **Given** 上次保存 1 小时前，离线效率 0.5，在线速率 10 berries/s，**When** `computeOffline`，**Then** gain.berries === `10 * 3600 * 0.5 = 18000`。
  2. **Given** 离线 100 小时，封顶 8 小时，**When** 计算，**Then** `capped === true` 且 secondsElapsed === 28800。
  3. **Given** savedAt === now（同秒打开），**When** 计算，**Then** gain 全 0、不报错。
  4. **Given** 离线结果包含 berries=18000，**When** `applyOffline`，**Then** 当前 berries 累加成功。
  5. **Given** 系统时间被手动改到 savedAt 之前（时间倒流），**When** 计算，**Then** secondsElapsed 钳到 0，不给负收益。

### 1.8 save system（`game/systems/save.ts`）

- **职责**：把 zustand 5 个 slice 序列化到 localStorage、反序列化、做版本迁移。
- **输入**：
  ```ts
  const SAVE_KEY = 'high_save';
  const CURRENT_VERSION = 1;

  interface SaveData {
    version: number;
    savedAt: number;
    resources: Record<ResourceKey, [number, number]>; // Decimal → [mantissa, exponent]
    buildings: BuildingInstance[];
    workers: WorkerState[];
    tech: TechState;
    stage: StageState;
  }

  function saveNow(): void;
  function loadNow(): SaveData | null;
  function hydrateAll(save: SaveData): void;          // 把数据灌进 5 个 slice
  function serialize(): string;                       // JSON.stringify
  function deserialize(raw: string): SaveData | null; // JSON.parse + schema 校验
  function migrate(raw: any): SaveData;               // 见 §3.3
  ```
- **输出**：localStorage.setItem / getItem；`hydrateAll` 同步触发所有 store setState。
- **持有状态**：无（纯函数 + localStorage I/O）。
- **依赖 / 被依赖**：
  - 依赖：5 个 slice、`balance.ts`（默认值）。
  - 被依赖：`main.tsx`（启动）、`game/loop.ts`（debounce 调用）、`visibilitychange` 监听。
  - **越层检查**：✅。
- **关键测试点**：
  1. **Given** 当前 state 有 berries=12345，**When** `serialize()`，**Then** JSON 里 resources.berries === [1.2345, 4]（Decimal 正确拆分）。
  2. **Given** 写盘后清空内存再 `loadNow()`，**When** `hydrateAll`，**Then** berries 仍为 12345。
  3. **Given** localStorage 里是 v0（version=0，没有 tech 字段），**When** `migrate`，**Then** 输出 version=1 且 tech.researched=[]（默认值补齐）。
  4. **Given** localStorage 里是被手动篡改成非法 JSON，**When** `deserialize`，**Then** 返回 null 而不是抛异常（启动不白屏）。

### 1.9 name generator（`game/systems/nameGenerator.ts`）

- **职责**：按 ADR 007 生成英文名 + 音译中文（"Groog" → "格鲁格"），保证不重复。

  ```ts
  interface GeneratedName { en: string; zh: string; }
  function generateWorkerName(existingNames: Set<string>, rng?: () => number): GeneratedName;
  ```
- **输出**：随机生成；重名时递归重试（最多 N 次后加数字后缀）。
- **持有状态**：无（纯函数，重名靠入参 `existingNames` 去重）。
- **依赖 / 被依赖**：
  - 依赖：内置 syllable 表（元音/辅音/中文音译映射，写在同文件或 `game/data/names.json`）。
  - 被依赖：`workers.ts`（recruit 时调）。
  - **越层检查**：✅。**注意**：放 game/systems 而非 scene，是为了在 Node 单测里直接跑、不依赖 Phaser。
- **关键测试点**：
  1. **Given** 空 existingNames，**When** 调 100 次，**Then** en 和 zh 都非空，且字符串长度在 3~12 之间。
  2. **Given** existingNames 已含 "Groog"，**When** 强制 rng 让首字母组合都撞 "Groog"，**Then** 重试后返回 "Groog2" 之类后缀。
  3. **Given** 固定 rng 种子，**When** 调 2 次，**Then** 两次结果一致（可重复，便于测试存档）。
  4. **Given** 任意输出，**When** 检查 zh，**Then** 只含汉字（不允许中英混排）。

### 1.10 pathfinding 封装层（`scene/pathfinding.ts`）

- **职责**：对 easystarjs 做薄封装，隐藏 EasyStar 实例细节，提供 Promise 化 API 和路径缓存。
- **输入**：
  ```ts
  interface Tile { x: number; y: number; }
  interface PathGrid {
    width: number;
    height: number;
    walkables: number[];   // 可通行的 tile 类型 id
  }

  class PathFinder {
    setGrid(grid: PathGrid, costMap?: Record<number, number>): void;
    findPath(from: Tile, to: Tile): Promise<Tile[]>;   // 找不到 reject
    clearCache(): void;
    destroy(): void;
  }
  ```
- **输出**：resolve 为 waypoint 数组（不包含起点，包含终点）；reject 为 PathNotFoundError。
- **持有状态**：内部 `EasyStar` 实例 + `Map<string, Tile[]>` 路径缓存（key = `${from.x},${from.y}->${to.x},${to.y}`）。
- **依赖 / 被依赖**：
  - 依赖：`easystarjs`、Phaser（仅在 Phaser 场景内 new）。
  - 被依赖：`scene/GameScene.ts`、`scene/WorkerSprite.ts`。
  - **越层检查**：✅ 它在 scene/，不 import React；它不写 zustand。
- **关键测试点**（在 jsdom + fake easystar 下测逻辑；真实寻路靠 M1 手动验证）：
  1. **Given** 20×20 全通网格，**When** `findPath({0,0},{5,5})`，**Then** resolve 路径长度 ≤ 10（曼哈顿距离）。
  2. **Given** 中间一堵墙挡死，**When** 寻路，**Then** reject PathNotFoundError。
  3. **Given** 同一对 from/to 第二次寻路，**When** 调用，**Then** 直接走缓存（用 spy 断言 easystar.findPath 只调一次）。
  4. **Given** `clearCache()` 后再寻路，**When** 调用，**Then** 重新走 easystar。

### 1.11 WorkerSprite 类（`scene/WorkerSprite.ts`）

- **职责**：单个工人的视觉表现（贴图、行走 tween、状态动画），订阅 workers slice 来同步自己的 `visual` 字段。

### 1.14 游戏主循环 tick 调度器（`game/loop.ts`）

**选型：`requestAnimationFrame` + 固定步长时间累加器（Fixed Timestep Accumulator）**。

> **为什么不用 setInterval**：Chrome 在后台标签页把 setInterval throttle 到 1Hz，挂机游戏切后台再切回来会跳一大段，且误差累积。
> **为什么不用纯 rAF 跑逻辑**：显示器刷新率 60/90/120Hz 不一，逻辑速度会随帧率波动；掉帧时产出速率跟着掉，玩家会投诉。
> **为什么不用"每帧乘 delta"**：挂机游戏数值很大，浮点误差在几万次 tick 后累积；固定步长是 Glenn Fiedler《Fix Your Timestep》的标准做法。

```ts
// game/loop.ts
const FIXED_DT = 0.1;          // 100ms 一个逻辑 tick
const MAX_FRAME_TIME = 1;      // 切后台回来最多补 1 秒逻辑，剩余走 offline
const SAVE_DEBOUNCE_MS = 2000;
const SAVE_INTERVAL_MS = 30_000;

class GameLoop {
  private acc = 0;
  private last = 0;
  private rafId = 0;
  private saveTimer: ReturnType<typeof setTimeout> | null = null;

  start() {
    this.last = performance.now();
    const step = (now: number) => {
      let frame = (now - this.last) / 1000;
      this.last = now;
      if (frame > MAX_FRAME_TIME) frame = MAX_FRAME_TIME;

      this.acc += frame;
      while (this.acc >= FIXED_DT) {
        tickProduction(FIXED_DT);
        useTech.getState().tickResearch(FIXED_DT);
        useStage.getState().updateProgress(FIXED_DT);
        this.acc -= FIXED_DT;
      }
      this.debouncedSave();
      this.rafId = requestAnimationFrame(step);
    };
    this.rafId = requestAnimationFrame(step);

    // 兜底定期存档
    setInterval(() => saveNow(), SAVE_INTERVAL_MS);
    // 切后台 / 关页立即存
    document.addEventListener('visibilitychange', () => {
      if (document.hidden) saveNow();
    });
  }

  private debouncedSave() {
    if (this.saveTimer) clearTimeout(this.saveTimer);
    this.saveTimer = setTimeout(() => saveNow(), SAVE_DEBOUNCE_MS);
  }

  stop() { cancelAnimationFrame(this.rafId); }
}
```

- **职责**：驱动所有纯逻辑 tick，不碰渲染；Phaser 自己的 `update()` 只做视觉插值。
- **持有状态**：`acc / last / rafId / saveTimer`。
- **依赖 / 被依赖**：
  - 依赖：`production.ts`、`tech.ts`、`stage.ts`、`save.ts`。
  - 被依赖：`main.tsx`。
  - **越层检查**：✅ 在 game/，不 import Phaser。Phaser 动画自己跑自己的 rAF。
- **关键测试点**：
  1. **Given** FIXED_DT=0.1，模拟 frame=0.35，**When** 跑一帧，**Then** tickProduction 被调用 3 次（0.1×3），acc 余 0.05。
  2. **Given** frame 被强制设为 5 秒（模拟切后台），**When** 跑一帧，**Then** 只补 10 个 tick（MAX_FRAME_TIME 钳制），其余时间留给 offline。
  3. **Given** 连续 add 资源 100 次，**When** 2 秒后，**Then** saveNow 只被调用 1 次（debounce 生效）。
  4. **Given** 页面 visibilitychange → hidden，**When** 触发，**Then** saveNow 立即被调用（不等 debounce）。

### 1.15 事件总线设计（`game/events/bus.ts`）

新增文件（目录结构里没列，建议补进 `game/`）。三选一的边界：

| 通道 | 用途 | 谁发 | 谁收 |
| --- | --- | --- | --- |
| **zustand store** | 持久状态、UI 渲染源 | 所有层 | React hook、scene subscribe |
| **`mitt` bus（本文新增）** | 跨层**瞬时命令**，不带持久状态 | UI / scene | scene / game systems |
| **Phaser EventEmitter** | scene 内部（WorkerSprite ↔ GameScene ↔ map） | scene 内 | scene 内 |

**为什么需要 mitt**：UI 点"招募工人"按钮时，UI 只调 `workers.recruit()`（写 zustand），但 Phaser 要在地图上**立刻**生成 sprite——如果走 zustand subscribe，会晚一个 render cycle 且难以携带 `homeTile` 这种一次性参数。bus 就是干这个的。

```ts
// game/events/bus.ts
import mitt from 'mitt';

type GameEvents = {
  // UI → scene
  'ui:recruitWorker':    { homeTile: Tile };
  'ui:buyBuilding':      { type: BuildingTypeId; tile: Tile };
  'ui:upgradeBuilding':  { uid: string };
  // scene → game systems
  'scene:workerArrived': { workerId: WorkerId; tile: Tile };
  'scene:pathNotFound':  { workerId: WorkerId };
  // game systems → scene / UI
  'stage:changed':       { from: StageId; to: StageId };
  'offline:shown':       { seconds: number; gain: Partial<Record<ResourceKey, Decimal>> };
};

export const bus = mitt<GameEvents>();
```

- **职责**：跨层瞬时命令的发布订阅，带类型约束。
- **持有状态**：无（mitt 实例本身）。
- **依赖 / 被依赖**：依赖 `mitt`；被 scene、ui、main 用。**放 game/ 层**，因为它不依赖 Phaser 也不依赖 React，纯 TS。
- **关键测试点**：
  1. **Given** 监听 `ui:buyBuilding`，**When** emit 一次，**Then** handler 收到 payload。
  2. **Given** `bus.off('ui:buyBuilding', handler)`，**When** 再 emit，**Then** handler 不再被调（防 HMR 泄漏）。
  3. **Given** emit 一个未在 GameEvents 里声明的事件名，**When** TypeScript 编译，**Then** 编译报错（类型安全）。

## 2. 数据流与时序图（文字版）

### 2.1 一帧完整链路（玩家看到的一切是怎么串起来的）

```
[浏览器 rAF 触发]
   │
   ├─→ A. Phaser 自己的 rAF（Phaser 内置）
   │     └─ GameScene.update(time, delta)
   │         ├─ WorkerSprite.update()：按 tween 推进小人像素位置
   │         ├─ 不读 zustand 最新值（动画位置由 tween 自己算）
   │         └─ 仅在小人到达 waypoint 时 emit 'scene:workerArrived'
   │
   └─→ B. 我们的 GameLoop.start() 里的 rAF（game/loop.ts）
         │
         ├─ acc += frame（钳到 1 秒）
         ├─ while (acc >= 0.1) {
         │    ├─ production.tickProduction(0.1)
         │    │     └─ useResources.getState().add(...)
         │    ├─ tech.tickResearch(0.1)
         │    └─ stage.updateProgress(0.1)
         │  }
         │
         └─ debouncedSave()（2 秒防抖写 localStorage）

[zustand set 触发订阅]
   │
   ├─→ useResources hook（在 ResourceBar.tsx 里）
   │     └─ React scheduler 重渲染 → 顶部资源数字 "1,234" → "1,235"
   │
   └─→ useWorkers.subscribe（在 WorkerSprite 构造时）
         └─ syncVisual(worker) → 切 Phaser 动画帧（gathering/walking）
```

**关键澄清**：
- 资源数字刷新**不经过 Phaser**，直接 zustand → React。
- 小人行走动画**不经过 zustand**，Phaser tween 自己跑；zustand 只存"他在干嘛"（visual 字段），sprite 订阅后切动画。
- 一帧里 A 和 B 是**两个独立 rAF 回调**，Phaser 内部一个、我们一个。不要把逻辑 tick 塞进 `GameScene.update`，否则 Phaser 暂停（如 devtools 打开）会冻结挂机。

### 2.2 存档时机

| 时机 | 触发方式 | 说明 |
| --- | --- | --- |
| 资源/建筑/工人变化后 | `debounce 2s` | 防止高频写 localStorage 卡 UI |
| 每 30 秒 | `setInterval` | 兜底，防止 debounce 被持续变化的资源"饿死" |
| `visibilitychange → hidden` | 立即 `saveNow()` | 切后台、切标签页时立刻落盘 |
| `beforeunload` | 立即 `saveNow()` | 关标签页 / 关浏览器 |
| 阶段切换 / 研究完成 | 立即 `saveNow()` | 关键里程碑事件，不冒丢失风险 |

**为什么不全 setInterval**：玩家关浏览器前那一刻的进度会丢最多 30 秒。
**为什么不每次资源 add 都写**：localStorage 是同步 I/O，挂机游戏一秒几十次 add，会卡死主线程。

### 2.3 启动时序（冷启动）

```
main.tsx
  │
  1. raw = localStorage.getItem(SAVE_KEY)
  2. if (raw) {
  3.   save = deserialize(raw)
  4.   save = migrate(save)            // 版本迁移
  5.   now = Date.now()
  6.   offline = computeOffline(save, now, BALANCE.offline)
  7.   hydrateAll(save)                 // 5 个 slice 灌数据
  8.   applyOffline(offline.gain)       // 叠加离线收益
  9.   bus.emit('offline:shown', ...)   // UI 弹"你离开了 X 秒，获得 Y"
     } else {
       // 首次启动：用 balance.ts 初始值 hydrate
     }
  10. new Phaser.Game({ scene: [GameScene] })
  11. GameScene.create()
       ├─ load tilemap
       ├─ 读 useBuildings.getState().list → addImage
       ├─ 读 useWorkers.getState().list → spawnWorker（入池）
       └─ subscribe 后续变化
  12. <App /> 挂载（React 面板）
  13. gameLoop.start()   ← 最后启动，前面数据都就绪
```

**为什么 offline 在 hydrate 之后**：offline 公式需要 buildings/workers/tech 的完整快照才能算。
**为什么 gameLoop 最后 start**：避免 tick 跑到一半 zustand 还没 hydrate。

## 3. 横切关注点技术方案

### 3.1 同屏多小人性能（v1 目标：同屏 ≤ 50 个工人不掉帧）

| 技术 | Phaser 具体做法 |
| --- | --- |
| **对象池** | `WorkerSprite` 不 destroy 不 create，`GameScene` 维护 `Array<WorkerSprite>` 空闲池 + 在用池；回收时 `setActive(false).setVisible(false)` 回池；新工人从池里 `get()`，复位位置/动画。 |
| **寻路缓存** | `PathFinder` 内部 `Map<key, Tile[]>`，key 用 `from + '->' + to`；同起点同终点直接命中；建筑被拆 / 地形变化时 `clearCache()`。 |
| **离屏剔除** | Phaser 3 Camera 默认有 cull，sprite 加 `setCullPadding(8, 8)`；超出视野的 worker `setActive(false)` 不跑 tween 回调。 |
| **动画帧复用** | 所有工人共用一张 texture atlas（`workers.png`），`AnimationManager.create({key:'walk', frames: this.anims.generateFrameNumbers('workers', ...)})` 只注册一次；所有 WorkerSprite `play('walk')` 复用同一动画实例。 |
| **物理简化** | 工人不用 Arcade Physics 做碰撞，纯 tween + `moveTo` 回调；碰撞（如两人重叠）v1 不处理，视觉重叠可接受。 |
| **数量硬上限** | `balance.ts` 里 `MAX_WORKERS = 50`，超过则招募按钮 disabled，不进入"60 个工人抢资源点"这种坑。 |

### 3.2 手机端响应式

- **Phaser 画布**：用 Phaser 3 的 Scale Manager，`mode: Phaser.Scale.FIT`，`autoCenter: CENTER_BOTH`，`parent: document.getElementById('game-container')`；监听 `resize` 事件重新算缩放。逻辑分辨率固定 960×540（16:9），手机上按比例缩。
- **UI 断点**：Tailwind 3，`md:` (768px) 以下 BuildMenu 改成底部抽屉（fixed bottom sheet），TechTree 改成全屏 modal。
- **PWA**：Vite 装 `vite-plugin-pwa`，生成 manifest.json + service worker；图标用像素风占位。M3 里程碑上线 itch.io 时开。
- **触控**：Phaser 输入 `pointerdown` 兼容鼠标和触摸；UI 按钮 `touch-action: manipulation` 防止双击缩放。

### 3.3 存档版本迁移（migrations 数组）

```ts
const migrations: Record<number, (raw: any) => any> = {
  0: (raw) => ({
    ...raw,
    version: 1,
    tech: { researched: [], researchProgress: 0 },
    stage: { current: 'primitive', unlocked: ['primitive'], progress: 0 },
  }),
  // 未来 v2：
  // 1: (raw) => ({ ...raw, version: 2, resources: { ...raw.resources, magic: [0, 0] } })
};

function migrate(raw: any): SaveData {
  let data = raw;
  while ((data.version ?? 0) < CURRENT_VERSION) {
    const v = data.version ?? 0;
    if (!migrations[v]) throw new Error(`No migration for v${v}`);
    data = migrations[v](data);
  }
  return data as SaveData;
}
```

**规则**：
- 每个版本一个 migration，只做"补字段 / 改结构"，**不**做数值重算（数值重算属于 balance 调整，单独发版）。
- migration 必须幂等（v1 → v2 跑两次结果一样）。
- 每个 migration 配一个 fixture：`__tests__/fixtures/save_v0.json`，测试"喂 v0 存档 → 得到 v1"。

### 3.4 大数字（break_infinity.js）

- **zustand 里怎么存**：`resources.values[ResourceKey] = Decimal`（break_infinity.js 的 Decimal 实例）。
  - Decimal 的运算是**不可变**的（`a.add(b)` 返回新实例），天然契合 zustand 浅比较。
  - **不要**在 state 里存 `Decimal` 又在 React 里 `toString()` 直接渲染——Decimal 默认 toString 会输出 `1.234567e45`，v1 可以接受；后续要中文缩写再加 formatter。
- **React 渲染**：`ui/components/FormatNumber.tsx`：
  ```tsx
  function FormatNumber({ value }: { value: Decimal }) {
    // v1：直接 toExponential(2) → "1.23e45"
    // 后续 v2：>= 1e6 显示 "1.23M" / "1.23B" / 中文 "1.23后"
    return <span>{value.toExponential(2)}</span>;
  }
  ```
- **序列化**：Decimal 不能直接 JSON.stringify（会丢 mantissa/exponent），必须 `[d.mantissa, d.exponent]` 元组；反序列化时 `new Decimal([m, e])`。
- **陷阱**：不要做 `Number(decimal)` 转 JS number，超过 `1e308` 直接变 Infinity。所有运算留在 Decimal 内部。

### 3.5 防作弊初版（v1 接受改 localStorage，v2 预留接口）

- **v1 立场**：单机挂机，玩家改 localStorage 是他自己的事，不花成本防。但代码里要**埋好接口**，v2 上后端时不用改业务代码。
- **接口预留**：
  ```ts
  // game/systems/clock.ts（M0 就建空文件，M4 填实现）
  export interface Clock {
    now(): number;          // v1: Date.now()；v2: 服务端时间偏移校准
    getServerTimeOffset(): number;
  }
  export const clock: Clock = {
    now: () => Date.now(),
    getServerTimeOffset: () => 0,  // M4 接入 /api/time 后填
  };
  ```
- **所有读时间的地方**：离线结算、saveNow 的 savedAt、gameLoop 的 last，**统一走 `clock.now()`**，禁止裸 `Date.now()`。这样 v2 换服务端校时时只改 clock.ts 一处。
- **v2 计划**：
  - 启动时 `GET /api/time` 拿服务端时间，算 `offset = serverNow - Date.now()`。
  - 离线结算时用 `savedAt + offset` 与 `now + offset` 差值，玩家改本地系统时间无效。
  - 云端存档时服务端二次校验：如果客户端报的离线收益 > 服务端按自己时间戳算的收益，按服务端值取小。

## 5. 对其他角色的挑战

### 5.1 对主策划：这套架构下哪些玩法需求会很痛？

1. **"每个小人有独立记忆 / 情绪 / 性格"**：当前 `WorkerState` 只有 visual 状态，要加情绪系统意味着 workers slice 字段膨胀，且情绪要影响生产速率——会逼 production 系统读 N 个情绪字段。**建议 v1 砍掉**，v2 再考虑。
2. **"玩家手动指挥每个小人去某处"**：当前架构是建筑分配制（assignedBuildingUid），工人自动往返。要加"点地指派"需要 UI → bus → scene → pathfinding → workers 状态机，工作量约 3 天，且和对象池/寻路缓存强耦合。**建议 v1 不做**。
3. **"实时战斗 / 怪物袭击"**：当前 production 是 100ms 纯函数 tick，没有伤害、HP、死亡事件流。加战斗需要新的 combat system + 工人 dead 状态 + 敌人 sprite 池，**和挂机节奏冲突**，建议放到资料片而非 v1。
4. **"玩家能拆建筑、能移动建筑"**：buildings store 当前只有 buy/upgrade/assign，没有 demolish/move。move 会触发寻路缓存失效，需要 `clearCache()`，工作量 0.5 天但容易漏。
5. **"多人同时在线合作"**：当前是单机 zustand + localStorage，要做联机需要把整个 GameState 变成可同步的 CRDT 或权威服务端模拟，**等于重写**。明确不在路线图里。

### 5.2 对数值策划：balance.ts 怎么组织才不变成上帝文件？

**当前约定**是"数值集中在 balance.ts"。但如果不拆，200 个建筑 × 5 个阶段 × 3 个资源 = 3000 行单文件，谁都不敢改。建议：

```
game/systems/balance/
  ├── index.ts          ← 聚合导出，业务代码只 import from '../balance'
  ├── global.ts         ← MAX_WORKERS, OFFLINE_EFFICIENCY, FIXED_DT
  ├── resources.ts      ← 资源初始值、存储上限
  ├── buildings.ts      ← 每个建筑的成本、产出速率、工人上限
  ├── workers.ts        ← 招募成本、工效系数
  ├── techs.ts          ← 每个科技的成本、加成
  └── stages.ts         ← 每阶段解锁条件、产出倍率
```

**规则**：
- `index.ts` 只做 `export * from './buildings'` 这种聚合，业务方 `import { BUILDINGS } from '@/game/systems/balance'` 一个入口。
- 静态数值优先放 `data/*.json`（程序读 JSON），**代码里只放"公式"和"倍率"**，不要把一张数值表硬编码进 .ts。
- 每次调平衡只改一个文件，PR 里一目了然。
- 加新建筑 = 改 `data/buildings.json` + `balance/buildings.ts` 加一行配置引用，不动业务代码。

### 5.3 对 QA：哪些模块测试成本最高，建议砍需求或简化？

1. **offline.ts（最高风险）**：时间相关、边界多（时间倒流、跨月、跨年、最大封顶、效率系数）。**建议**：v1 先把 maxSeconds 设小（比如 4 小时），减少"挂一周回来"的极端 case；所有时间走 `clock.now()` 便于 mock。
2. **save.ts 版本迁移**：每加一个字段就要补一个 migration + fixture。**建议**：v1 阶段频繁迭代时，**允许 break change**——存档版本号锁死 1，删字段不做迁移，提示玩家"旧档作废"。v1.x 稳定后再开 migration 流程。
3. **大数字 Decimal**：1e308 以上、mantissa/exponent 边界、序列化往返。**建议**：v1 数值范围压在 1e15 以内（挂机一周内达不到），不引入中文缩写，只做 toExponential。
4. **同屏多工人性能**：50 个工人 + 寻路缓存 + 对象池，性能问题只能真机测。**建议**：v1 硬上限 20 人而非 50 人，M5 再提。
5. **手机 PWA**：iOS Safari 对 service worker 限制多（不能后台跑），"添加到主屏幕"体验差。**建议**：M3 先上 H5，PWA 只做 Android，iOS 接受"加到主屏幕就是个全屏书签"。

### 7.1 "通关"的三层定义与架构对应

| 层级 | 04c/04a 定义 | 架构上对应什么 | v1 是否实现 |
| --- | --- | --- | --- |
| **主线通关** | 建成发射台 + 发射第一枚火箭 | `stage.current === 'space'` 且 `rocketsLaunched >= 1` | ✅ M5 |
| **阶段通关** | 六阶段各跃迁一次 | `stage.unlocked.length === 6`，每次切换发 `stage:changed` 事件 | ✅ M1-M5 自然落地 |
| **终局内容** | 戴森球、星尘累积、成就、每日挑战 | `meta.prestigeCount`、`meta.achievements`、`meta.dailySeed` | v1 只留 schema，数值见 §8 |

**架构决定**：把"是否通关"做成一个**可查询的派生字段**，而不是散落在各处的布尔。

```ts
// game/systems/progress.ts（v1 新增，纯函数）
interface ProgressSnapshot {
  currentStage: StageId;
  rocketsLaunched: number;
  isMainlineCleared: boolean;      // rocketsLaunched >= 1
  prestigeCount: number;           // v1 = 0，v2 启用

function computeProgress(state: GameState): ProgressSnapshot;
```

**为什么要抽出来**：
- 离线结算、成就、UI 横幅、"通关画面"都要查"是否已通关"，不能每个地方都 `stage === 'space' && launched >= 1` 写一遍。
- debug 倍速跑通关时，只看 `isMainlineCleared` 一个布尔就能断言，不用查 5 个字段。

### 7.2 总时长目标对架构的硬约束

04c 定的三档：纯在线 18h / 每天挂 8h 共 3 天 / 24h 挂机 5–7 天。这三个数字对架构意味着：

| 约束 | 架构要求 |
| --- | --- |
| **5 分钟演示不劝退** | M1 必须在 60 秒内看到第一个正反馈（采到浆果）；前 5 分钟不能有任何"等加载" |
| **开发者自己能测完** | 必须有 debug 倍速（见 §7.4），1 小时跑完整条主线 |
| **朋友 20 分钟能看到村庄→小镇** | 存档 hydrate 后不能有"新手村还没走完就弹一堆面板"；UI 按 stage 渐进解锁 |
| **3 天挂机成立** | 离线结算必须是 **wall-clock 差值**，不能依赖 rAF tick 累积（见 §7.3） |
| **24h 挂机不崩** | 离线收益按阶段硬 cap（04c §1.6），超过 cap 部分丢弃；不允许把 3 天算成 3×8h |

### 7.3 离线结算怎么设计，才能让"5 分钟演示"和"3 天挂机"都成立

**核心矛盾**：
- 5 分钟演示：玩家希望"点一下立刻看到数字涨"，所以在线 tick 是 100ms 固定步长，反馈要快。
- 3 天挂机：玩家不可能 3 天不切后台，rAF 在后台会被浏览器冻结。如果靠 rAF 累积 dt，3 天后回来 dt 累加值可能是 259200 秒，直接把 break_infinity 干到 e308。

**解法：双时间源，严格分离**

```
在线时间（active time）   → 由 rAF 驱动的 fixed timestep accumulator（§1.14）
                            只在页面可见时累积；用于"看见小人干活"

离线时间（wall-clock）    → 由 clock.now() - lastSavedAt 直接算
                            不经过 accumulator；用于离线结算
```

**关键规则**：

1. **在线 tick 不累积"离线秒数"**。即 `GameLoop.acc` 只负责在线逻辑，切后台时 rAF 停，`acc` 停；回来时 `frameTime = clamp(frameTime, 0, 1)`（§1.14 已定），**最多补 1 秒**，剩下的 3 天走 offline 结算。
2. **离线结算公式**（对齐 04c §1.6）：
   ```ts
   function computeOffline(state, savedAt, now): OfflineResult {
     const stage = state.stage.current;
     const cap = STAGE_OFFLINE_CAP[stage];          // 2h/8h/12h/24h/36h/48h
     const eff = STAGE_OFFLINE_EFF[stage];          // 0.25/0.40/.../1.0
     const rawSeconds = Math.max(0, now - savedAt); // 时间倒流钳 0
     const usedSeconds = Math.min(rawSeconds, cap);
     const rate = computeProductionRatePerSecond(state);  // 纯函数，不 tick
     const gain = scaleProduction(rate, usedSeconds * eff);
     return { gain, usedSeconds, capped: rawSeconds > cap };
   }
   ```
3. **`computeProductionRatePerSecond` 必须是纯函数**，和 `tickProduction(dt)` 共用同一份建筑/科技查表。**不允许**在线 tick 用一套公式、离线用另一套——04d §F4 明确要求"倍速下离线公式必须和正常速度一致"。
4. **存档时机**（§2.2 已定）：每次结算完把 `lastSavedAt = clock.now()` 写盘。这样即使玩家挂 3 天，回来只结算一次，不会重复发钱（04d A6）。
5. **离线不触发的东西**（对齐 04c §5.3）：科技点、人口自然增长、随机事件、阶段跃迁。离线结算只做 `resources.add`，**不**调 `tech.tickResearch`、**不**调 `workers.recruit`、**不**发 `randomEvent:*`。

**为什么这样"5 分钟演示"和"3 天挂机"都成立**：
- 5 分钟演示：玩家在线，rAF 100ms tick，小人真在跑，资源真在涨——**走的是 accumulator 通道**。
- 3 天挂机：玩家切后台，rAF 冻结；回来打开页面，启动时序（§2.3）第 6 步 `computeOffline` 一次算完 3 天收益——**走的是 wall-clock 通道**。
- 两个通道**共用一份产出公式**，但时间源完全独立，互不污染。

### 7.4 debug 倍速模式（QA §7.2 硬要求，架构必须支持）

**接口草案**（M2 前落地，对齐 04d P0）：

```ts
// game/systems/debug.ts
interface DebugHooks {
  enabled: boolean;
  timeScale: number;          // 1 = 正常，1000 = 倍速
  productionMultiplier: number; // 1 = 正常
  give: (r: ResourceKey, amt: Decimal | number) => void;
  unlockStage: (s: StageId) => void;
  reset: () => void;
}
export const debug: DebugHooks = {
  enabled: new URLSearchParams(location.search).has('debug'),
  timeScale: 1,
  productionMultiplier: 1,
  // ...
};
```

**怎么和 clock / loop 协同**：

1. **timeScale 作用在 clock 上，不作用在 rAF 上**。`clock.now()` 返回 `realNow + debugOffset * (timeScale - 1)`，这样：
   - 在线 tick 的 dt 不变（还是 100ms 固定步长），不会因为倍速把 accumulator 干爆。
   - 离线结算读 `clock.now()` 时自动被放大，等于"挂 3 秒 = 挂 3000 秒"。
2. **productionMultiplier 作用在 `computeProductionRatePerSecond` 的输出上**，不改 dt、不改 cost——这样 04d F4 用例"倍速下离线公式必须和正常速度一致"自动成立（因为公式里乘的是同一个 multiplier）。
3. **硬限制**：
   - `timeScale` 上限 ×10000（04d 已定）。
   - `debug.enabled` 必须从 URL query 读，打包发布版 tree-shake 掉（用 `import.meta.env.DEV` 守卫）。
   - debug 模式产生的存档打 `meta.debugUsed = true`，v2 接后端时服务端拒收。

**为什么不在 `GameLoop` 里乘 timeScale**：如果把 `frame = frame * timeScale`，accumulator 一次补 1000 个 tick，Phaser 渲染会卡死、React 会重渲染几百次。倍速必须只影响"时间读数"，不影响"帧率"。

### 7.5 六阶段 checkpoint（架构埋点，对齐 04d §7.4）

每个阶段切换时，`stage` slice 发 `stage:changed` 事件，debug 控制台监听后打印一行 checkpoint。架构上零成本：

```ts
// game/systems/debug.ts 里
bus.on('stage:changed', ({ from, to }) => {
  if (debug.enabled) console.log(`[checkpoint] ${from} -> ${to} @ ${computeProgress(...).playtimeSecondsOnline}s`);
});
```

**推荐**：每个阶段定义一个"最小可通过动作"（04d §7.4 表里已列），写进 `data/checkpoints.json`，debug 倍速下脚本按这个动作序列自动点按钮，跑完 6 个 checkpoint 用 < 3 分钟。

### 7.6 本章对当前设计的难度评估与推荐

| 子项 | 难度 | 推荐 |
| --- | --- | --- |
| 双时间源（active / wall-clock） | 低（已有 clock.ts 预留） | **v1 必做**，是离线收益的基石 |
| `computeProductionRatePerSecond` 抽纯函数 | 中（要把 production 拆成"速率查询"和"tick 应用"两半） | **v1 必做**，否则离线和在线两套数 |
| debug 倍速 | 中（要改 clock.ts，小心不要影响 rAF） | **M2 前必做**，QA 硬阻塞 |
| 6 阶段 checkpoint 脚本 | 低 | M3 前做，v1 可手动 |
| 开发者自己 18h 测完 | 低（靠 debug 倍速压到 1h） | 不做专门功能，靠 debug 控制台 |

## 8. 议题追加：可重玩性设计（程序架构视角）

> 与 `04c_数值草案.md` §8（星尘软 Prestige、mulberry32 种子、三流派、成就、每日挑战）、`04d_测试与体验.md` §8（meta/run 两层、注入 RNG、分支测试）对齐。

### 8.1 存档分两层：meta / run（v1 就必须分，04d P1）

**为什么 v1 必须分**：等 v2 想做硬 Prestige 时再分，要改 save.ts 序列化、所有 store hydrate、所有 migration——代价极大。现在分，成本只是 save.ts 里多两个字段。

```ts
// types/game.d.ts
interface MetaState {
  // —— 跨周目永久保留 ——
  prestigeCount: number;          // 通关次数，v1 = 0
  stardust: Decimal;              // 星尘，v1 = 0
  achievements: string[];         // 已解锁成就 ID
  settings: {
    musicVolume: number;
    sfxVolume: number;
    offlinePopupShown: boolean;
  };
  worldSeed: number;              // 本局种子，新开档时生成
  dailySeed: string;               // 每日挑战 seed（v1 留空）
  lastDailyResetDate: string;      // 'YYYY-MM-DD' UTC
  debugUsed: boolean;              // 是否开过 debug（v2 服务端拒收）
}

interface RunState {
  // —— 本周目状态，Prestige 时清空 ——
  resources: Record<ResourceKey, Decimal>;
  buildings: BuildingInstance[];
  workers: WorkerState[];
  tech: TechState;
  stage: StageState;
  rocketsLaunched: number;
  playtimeSecondsOnline: number;
  lastSavedAt: number;
}

interface SaveData {
  version: number;
  meta: MetaState;
  run: RunState;
}
```

**对现有架构的影响**：
- 5 个 slice 拆成两类：
  - **meta slice**（新增 `game/state/meta.ts`）：持有 `MetaState`，Prestige 时**不清空**。
  - **run slices**（resources/buildings/workers/tech/stage）：Prestige 时**重置回初始值**。
- `save.ts` 的 `serialize/deserialize` 天然适配：本来就按 slice 导出，现在只是多导一个 meta。
- **难度：低**。改动集中在 save.ts + 新 meta slice，不动 production/offline/progress。
- **推荐**：**v1 就分**。即使 v1 不做 Prestige，meta 里的 settings/achievements/worldSeed 也早就需要独立持久化。

### 8.2 Prestige / 转生系统（接口预留，v1 不实现）

**接口草案**（v2 启用，v1 只写空函数）：

```ts
// game/systems/prestige.ts（M5 建空文件，v2 填实现）
interface PrestigeResult {
  stardustGained: number;
  globalMultiplier: number;       // 1 + 0.10 * stardust
  runReset: RunState;             // 重置后的初始 run

function computePrestigeEarn(run: RunState): number;
function prestigeRun(meta: MetaState, run: RunState): { meta: MetaState; run: RunState };
```

**v1 必须做的预留**：
1. `meta.stardust`、`meta.prestigeCount` 字段在 schema v1 里就存在（默认 0）。
2. `production.computeProduction` 接受一个全局 multiplier 参数：
   ```ts
   function computeProduction(input, dt, globalMult: Decimal = new Decimal(1)) { ... }
   ```
   v1 永远传 1；v2 Prestige 后传 `1 + 0.10 * stardust`。**不要**在 production 里直接读 meta.stardust，否则 v2 改公式要重写。
3. `run.rocketsLaunched` 字段 v1 就加（即使 v1 只有 0/1）。

**难度评估**：
- v1 预留：**低**（加 3 个字段 + 1 个函数参数）。
- v2 真正实现：**中**（要做 Prestige UI、确认星尘公式、跑 P1-P5 测试）。
- **推荐**：v1 只做 schema 预留，不做 UI、不做数值。

### 8.3 世界种子（World Seed）与 RNG 注入

**架构决定**：所有随机数必须走一个可注入的 RNG 实例，**禁止裸 `Math.random()`**（04d R1-R5 硬要求）。

```ts
// game/systems/rng.ts
function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return function () {
    a |= 0; a = (a + 0x6D2B79F5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

interface Rng {
  next(): number;                       // [0, 1)
  int(min: number, max: number): number;
  pick<T>(arr: T[]): T;
  saveState(): number;                  // 当前位置（用于存档）
  loadState(s: number): void;
}

class SeededRng implements Rng { ... }

// 全局单例（game/ 层，不依赖 React/Phaser）
export const rng: Rng = new SeededRng(0);

// 启动时：rng.seed(meta.worldSeed)
```

**种子影响范围**（对齐 04c §8.2，只影响前 1 小时）：
- 初始资源点位置（浆果/石堆/树的 tile 坐标）——`scene/map.ts` 生成时调 `rng.int(...)`。
- 随机事件流——`game/systems/events.ts`（v2）。
- 小人名生成——`nameGenerator.ts` 已经接受 `rng?` 参数（§1.9），直接传 `rng`。
- **不影响**：建筑成本、产出速率、科技树结构。这些必须 deterministic，不能因 seed 变（04d S6）。

**存档里存什么**：
- `meta.worldSeed: number`——新档时 `Math.floor(Math.random() * 2**31)` 一次，之后这个档永远用这个 seed。
- **不要**存 RNG 内部计数（太碎），只存 seed；玩家读档后从 seed 重新生成前 1 小时的内容即可，后续事件流用"事件 ID + 种子"重算。

**难度评估**：
- RNG 注入 + mulberry32：**低**，半天。
- 把现有 `Math.random()` 全部替换：**中**，取决于代码里有多少处。建议 M0 就建 ESLint `no-restricted-syntax` 规则禁裸 `Math.random()`。
- 种子影响 map 生成：**低**，`scene/map.ts` 本来就参数化。
- **推荐**：M1 落地 RNG 注入；M2 让 nameGenerator 用 `rng`；M3 让 map 生成用 `rng`；随机事件流 v2 再说。

### 8.5 成就系统（埋点设计）

**原则：成就 = 监听已有事件，不在业务代码里埋 if**。

**事件总线新增事件名**（对齐 §1.15 的 GameEvents）：

```ts
type GameEvents = {
  // ...原有...
  'achievement:unlocked': { id: string; timestamp: number };

  // 业务事件（这些 v1 已经会发，成就系统订阅它们）
  'building:built':       { type: BuildingTypeId; totalCount: number };
  'worker:recruited':     { totalCount: number };
  'stage:changed':       { from: StageId; to: StageId };
  'tech:researched':     { id: TechId };
  'resource:cumulative':  { resource: ResourceKey; total: Decimal };  // 累计资源
  'rocket:launched':     { count: number };
  'prestige:completed':   { count: number };
};
```

**成就 store 草案**：

```ts
// game/state/achievements.ts
interface AchievementsSlice {
  unlocked: string[];                          // 已解锁 ID
  check: (event: GameEvents[keyof GameEvents], payload: any) => void;
  hydrate: (list: string[]) => void;
}

// game/systems/achievements.ts（规则表，纯数据）
const ACHIEVEMENT_RULES: AchievementRule[] = [
  { id: 'first_campfire',     on: 'building:built',  when: e => e.type === 'campfire' },
  { id: 'pop_10',             on: 'worker:recruited', when: e => e.totalCount >= 10 },
  { id: 'pop_50',             on: 'worker:recruited', when: e => e.totalCount >= 50 },
  { id: 'cum_berries_1m',     on: 'resource:cumulative', when: e => e.resource === 'berries' && e.total.gte(1e6) },
  { id: 'first_clear',        on: 'rocket:launched', when: e => e.count >= 1 },
  { id: 'three_clear',        on: 'prestige:completed', when: e => e.count >= 3 },
  // ...
];
```

**架构收益**：
- 业务代码**完全不知道成就存在**。`buildings.buy()` 只发 `building:built` 事件，不写"如果是 campfire 就解锁成就"。
- 加新成就 = 在 `ACHIEVEMENT_RULES` 里加一行，不动业务代码。
- 成就 UI 弹窗排队（04d A3）：unlocked 事件进来时 push 到队列，UI 一个个弹。

**难度评估**：
- 事件埋点（业务代码发 `building:built` 等）：**低**，本来就该发。
- AchievementsSlice + 规则表：**低**，半天。
- 弹窗 UI：**低**。
- 跨周目累计（04d A5）：**中**，需要明确"累计资源"是 run 内还是 meta 内——推荐放 meta（跨周目累计），这正好是 meta/run 分层的收益。
- **推荐**：M3 做成就系统框架，M5 填成就列表。

### 8.6 挑战模式（每日挑战 / 种子竞速）

**v1 立场**：v1 不做，但接口预留。

**每日种子公式**（对齐 04d D1-D4）：

```ts
// game/systems/dailySeed.ts
const DAILY_SALT = 'high-daily-v1';  // v1 硬编码盐，v2 换服务端下发

function getDailySeed(now: number): number {
  const d = new Date(now);
  const utcDate = `${d.getUTCFullYear()}-${d.getUTCMonth() + 1}-${d.getUTCDate()}`;
  return hashString(`${DAILY_SALT}:${utcDate}`);
}

// 跨天判定：用 UTC 日期，不用本地日期（04d D4）
function isNewDay(lastDate: string, now: number): boolean {
  const d = new Date(now);
  const utcDate = `${d.getUTCFullYear()}-${d.getUTCMonth() + 1}-${d.getUTCDate()}`;
  return utcDate !== lastDate;
}
```

**防改时间刷每日**（04d D2）：
- v1 单机：改系统时间就能刷，**接受**。
- v2：`meta.lastDailyResetDate` 存服务端，客户端时间不作数。

**挑战模式的存档隔离**：
- 每日挑战**不写主线存档**，单独一个 `localStorage` key `high_daily_YYYY-MM-DD`。
- 主线玩家可以"今天玩一把每日"，退出后不影响主线进度。
- 架构上只要 `save.ts` 接受一个 `storageKey` 参数即可：
  ```ts
  function saveNow(key: string = SAVE_KEY): void;
  function loadNow(key: string = SAVE_KEY): SaveData | null;
  ```

**难度评估**：
- 每日 seed 计算：**低**。
- 存档按 key 隔离：**低**（改 save.ts 签名）。
- debuff modifier 系统（×1.2-1.5）：**中**，需要在 `computeProductionRatePerSecond` 里乘一个 challenge modifier。
- 排行榜：**高**，依赖 M4 后端。
- **推荐**：v1 只做 `saveNow(key)` 参数化 + dailySeed 函数，UI 和 debuff v2 再说。
